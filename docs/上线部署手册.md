# 上线部署手册

> 适用版本：2026-09-18（阶段一：医护端 / 患者端 / 管理后台）
> 本手册按"照着做就能上线"编写。每一步都写了**怎么验证做对了**。

---

## 〇、先说清楚：哪些是实测过的，哪些没有

| 内容 | 状态 |
|---|---|
| 接口功能、权限、并发锁、故障演练、性能压测 | **本机实测通过**（详见《性能与故障演练报告》） |
| 数据库迁移 V1→V3、备份恢复命令 | **本机实测通过** |
| Docker 编排（`deploy/docker-compose.yml`） | **未实机验证**（开发机没有 Docker），按本文第 3–5 步走，遇到问题回报 |
| Nginx 配置 | 已按三前端架构重写，**未在真实域名 + 证书下验证** |

也就是说：**代码与数据库这一层是验证过的，容器与反向代理这一层需要你在服务器上跑一遍**。

## 一、上线前必须定下来的五件事

这五件事没定，后面会返工：

1. **域名**：例如 `followup.医院域名.cn`，并已备案（医院域名通常已备案）。
2. **HTTPS 证书**：医院一般有统一证书；没有就用 Let's Encrypt。
3. **服务器**：见下节规格。
4. **密钥保管方式**：`APP_CRYPTO_DATA_KEY` 与 `APP_CRYPTO_HASH_PEPPER` 是加密手机号的钥匙，
   **丢了所有手机号都无法解密**。上线前就要定好"抄在纸上锁抽屉"还是"存医院密码柜"。
5. **备份位置**：数据库备份放哪里、谁负责看、保留多久（默认 30 天）。

### 服务器规格建议

| 规模 | 配置 | 说明 |
|---|---|---|
| 一个科室（推荐起步） | 2 核 4G，50G SSD | 实测单机可支撑约 900 req/s；真实科室 10–30 并发，余量约 30 倍 |
| 全院多科室 | 4 核 8G，100G SSD | 应用与数据库建议分开 |

> 实测数据：1000 位患者 / 6010 个任务、20 并发的条件下，
> P50 43ms / P95 169ms / 失败率 0%（本机 2 核 4G 环境，与数据库同机）。

## 二、部署架构

```
                    ┌──────────── Nginx (443) ────────────┐
  手机浏览器 ───────►│  /          → 医护端 App            │
  微信/手机 ───────►│  /patient/  → 患者端 H5             │
  电脑浏览器 ───────►│  /admin/    → 管理后台              │
                    │  /api/      → 后端 8080             │
                    └──────────────┬──────────────────────┘
                                   │
                        ┌──────────▼──────────┐
                        │  Spring Boot 应用    │  -Xmx512m
                        └──────────┬──────────┘
                                   │ app_rw（非超级用户，行级安全依赖它）
                        ┌──────────▼──────────┐
                        │  PostgreSQL 16      │
                        └─────────────────────┘
```

**三个前端都是静态文件**（Vue 构建产物），不需要 Node 运行环境，由 Nginx 直接托管。

## 三、步骤 1：准备服务器

```bash
# 1) 安装 Docker 与 Compose 插件（以 Ubuntu 为例）
curl -fsSL https://get.docker.com | bash
docker --version && docker compose version

# 2) 时区必须是东八区：随访时间、逾期判断全依赖它
timedatectl set-timezone Asia/Shanghai
date    # 确认输出 +08:00

# 3) 只开放 22 / 80 / 443，数据库端口绝不对公网开放
ufw allow 22 && ufw allow 80 && ufw allow 443 && ufw enable
ufw status
```

> **验证**：`date` 显示 `+0800`，`ufw status` 里没有 5432。

## 四、步骤 2：取代码、生成密钥

```bash
git clone <仓库地址> /opt/followup && cd /opt/followup/deploy
cp .env.example .env
```

**生成随机密钥**（每个都要单独生成，不要复用）：

```bash
openssl rand -base64 32   # → DB_SUPERUSER_PASSWORD
openssl rand -base64 32   # → DB_APP_PASSWORD
openssl rand -base64 32   # → REDIS_PASSWORD
openssl rand -base64 32   # → APP_CRYPTO_DATA_KEY      ★ 必须单独备份
openssl rand -base64 32   # → APP_CRYPTO_HASH_PEPPER   ★ 必须单独备份
openssl rand -base64 32   # → APP_JWT_SECRET
```

把 `.env` 里的 `CHANGE_ME_*` 全部替换掉，并把 `SERVER_NAME` 改成真实域名。

> **验证**：`grep -c CHANGE_ME .env` 输出 `0`。
> **提醒**：`APP_CRYPTO_*` 两个值一旦上线不能再改，改了已存的手机号就解不开了。

## 五、步骤 3：构建前端与后端

三个前端共用一套 Node 依赖，构建产物分别是 `dist` / `dist-patient` / `dist-admin`。

```bash
cd /opt/followup/frontend
npm ci
npm run build           # 医护端   → frontend/dist
npm run build:patient   # 患者端   → frontend/dist-patient
npm run build:admin     # 管理后台 → frontend/dist-admin
ls -d dist dist-patient dist-admin    # 三个目录都要存在

cd /opt/followup/backend
mvn -s settings.xml -DskipTests clean package
ls -lh target/followup.jar
```

> **注意**：如果用 JDK 23 以上构建，`pom.xml` 已经显式声明了 Lombok 注解处理器路径，
> 不会再出现"找不到符号 getId()"那类问题（开发期踩过，已修）。
> **推荐仍用 JDK 21**：`JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64`。

把前端产物放到 Nginx 挂载目录：

```bash
mkdir -p /var/www/followup/{staff,patient,admin}
cp -r /opt/followup/frontend/dist/*          /var/www/followup/staff/
cp -r /opt/followup/frontend/dist-patient/*  /var/www/followup/patient/
cp -r /opt/followup/frontend/dist-admin/*    /var/www/followup/admin/
```

## 六、步骤 4：启动

```bash
cd /opt/followup/deploy
docker compose up -d
docker compose ps          # 四个容器都应是 running / healthy
```

> **验证**：`curl -s localhost/health` 返回 `{"status":"UP"}`（经 Nginx）。
> 或直连应用容器：`docker compose exec app curl -s localhost:8080/actuator/health`

## 七、步骤 5：初始化验证（**这一步不能省**）

### 5.1 确认数据库迁移全部执行

```bash
docker compose exec postgres psql -U pg_admin -d followup \
  -c "select version, description, success from flyway_schema_history order by version;"
```

必须看到 **V1 / V2 / V3 三条且 success = t**：

| 版本 | 内容 | 漏了会怎样 |
|---|---|---|
| V1 | 建表 43 张 + 行级安全 | 系统跑不起来 |
| V2 | 患者端行级安全加固 | **患者端可能读到别人的数据** |
| V3 | 热点查询索引 | 数据量大了会慢 |

### 5.2 确认应用连的是普通账号

```bash
docker compose exec postgres psql -U pg_admin -d followup \
  -c "select current_user;" 
# 在应用容器里执行：
docker compose exec app sh -c 'echo 应用连接账号见 DB_APP_USER'
```

**行级安全策略对超级用户无效**。`deploy/.env` 里的 `DB_APP_USER=app_rw` 不能改成
`pg_admin`，否则权限隔离会静默失效。

### 5.3 创建第一个管理员账号

演示种子数据**只在 dev 环境执行**，生产库是空的，所以第一个管理员要手工建：

```bash
docker compose exec postgres psql -U pg_admin -d followup
```

```sql
-- 1) 科室
INSERT INTO department (code, name, sort_no) VALUES ('XHNK', '消化内科', 1)
ON CONFLICT DO NOTHING;

-- 2) 管理员本人
INSERT INTO staff (dept_id, staff_no, name, gender, title, status, is_manager)
SELECT id, 'A0001', '系统管理员', 1, '信息科', 1, true
  FROM department WHERE code = 'XHNK';

-- 3) 账号：密码哈希要用应用生成，见下
```

密码哈希必须用 BCrypt 生成。最省事的做法是用开发机生成后拷过去：

```bash
# 在开发机执行（项目里已有依赖）
java -cp backend/target/followup.jar -Dloader.main=... # 或用一个临时 Java 类
```

更简单的办法：**临时把后端以 `dev` profile 启动一次**（会创建 A0001 / Followup@2026），
登录管理后台后立刻改密码，再把第一个真实管理员建出来。

> **验证**：用管理员登录 `/admin/`，能看到账号列表。

## 八、步骤 6：HTTPS

```bash
# 用 Let's Encrypt（医院有统一证书就直接放 certs 目录）
docker run --rm -v /etc/letsencrypt:/etc/letsencrypt \
  -v /var/www/certbot:/var/www/certbot certbot/certbot certonly \
  --webroot -w /var/www/certbot -d followup.医院域名.cn

mkdir -p deploy/nginx/certs
cp /etc/letsencrypt/live/followup.医院域名.cn/{fullchain.pem,privkey.pem} deploy/nginx/certs/
docker compose restart nginx
```

> **验证**：浏览器访问 `https://域名/` 无证书告警；`http://` 自动跳 `https://`。
> 证书到期前记得续期（certbot 可加 cron）。

## 九、步骤 7：上线自测（照着跑一遍）

在能访问服务器的机器上执行（脚本在 `tools/`）：

```powershell
# 1) 接口功能与权限：三套
powershell -File .\tools\api-smoke-test.ps1      -BaseUrl https://你的域名
powershell -File .\tools\portal-smoke-test.ps1   -BaseUrl https://你的域名
powershell -File .\tools\admin-smoke-test.ps1    -BaseUrl https://你的域名

# 2) 性能：并发 20、P95 必须 < 300ms、失败率必须 0
node tools\load-test.mjs --base https://你的域名 --concurrency 20 --duration 30

# 3) 故障演练：并发抢锁、注入、越权、边界
node tools\fault-drill.mjs   （改 BASE 环境变量指向线上）
```

> 注意：这些脚本会创建名为 `T8xxxx` / `T9xxxx` 的测试账号和一条回访记录。
> 生产环境跑完后请删掉测试账号，或只跑只读的 `load-test.mjs`。

## 十、日常运维

### 10.1 备份（**最重要**）

```bash
# 手动备份
docker compose exec -T postgres pg_dump -U pg_admin -d followup \
  | gzip > /backup/followup-$(date +%F-%H%M).sql.gz

# 保留 30 天，每天凌晨 2 点
crontab -e
0 2 * * * cd /opt/followup/deploy && ./scripts/backup-loop.sh
```

**每季度做一次恢复演练**（只备份不恢复，等于没备份）：

```bash
gunzip -c /backup/followup-2026-09-18-0200.sql.gz | \
  docker compose exec -T postgres psql -U pg_admin -d followup_restore_test
```

### 10.2 巡检清单（每周 5 分钟）

```bash
docker compose ps                    # 容器是否都 healthy
docker stats --no-stream             # 内存是否接近上限
df -h                                # 磁盘（备份会占空间）
docker compose exec postgres psql -U pg_admin -d followup -c \
  "select count(*) from login_log where success = false and created_at > now() - interval '1 day';"
# ↑ 失败登录突增 = 有人在试密码
```

## 十一、升级与回滚

```bash
# 升级
cd /opt/followup && git pull
npm run build && npm run build:patient && npm run build:admin   # 重新构建前端
cp -r frontend/dist*/* /var/www/followup/...                    # 更新静态文件
docker compose build app && docker compose up -d app            # 更新后端

# 回滚
git checkout <上一个版本> && 重新构建并部署
# 数据库迁移不回滚（Flyway 也不建议向下回滚），如确需回滚结构，
# 用升级前的备份恢复到新库再切换
```

> **铁律**：数据库结构变更必须走 `db/migration/V*.sql` 新文件，禁止手工改线上库。

## 十二、常见故障处理（现象 → 原因 → 处理）

| 现象 | 原因 | 处理 |
|---|---|---|
| 页面白屏 | 前端静态文件没放对 / 路径不对 | `ls /var/www/followup/staff` 应有 `index.html` 和 `assets/` |
| 接口 502 | 后端没起来 | `docker compose logs app \| tail -50`，看是否端口占用或数据库连不上 |
| 接口 401 一直登录失败 | 系统时间不对，JWT 时间戳偏差 | `date` 必须是 `+0800` |
| 数据库重启后接口报忙 | 连接池正在重建 | 实测**自动恢复**，无需重启；若 30 秒仍不通再看日志 |
| 管理员进不去后台 | 账号不是管理员 | 检查 `staff.is_manager` 或 `staff_role` 里是否有 `SUPER_ADMIN`/`DEPT_MANAGER` |
| 护士看不到患者 | 患者未加入搭档组 | 检查 `patient_care_team` 是否有 `ACTIVE` 记录（行级安全依赖它） |
| 两位护士同时点"立即回访" | 正常：只有一人能拿到 | 后到者会看到"该任务正在被其他同事处理"，30 分钟后锁自动失效 |
| 手机号解密失败 | `APP_CRYPTO_DATA_KEY` 被改过 | **不可恢复**，只能用备份 + 原密钥重建 |
| 磁盘被日志占满 | Docker 日志未限制 | compose 里已配 `json-file` 限 10MB×3，若改过请确认 |

## 十三、上线前安全清单（逐条打勾）

- [ ] `.env` 里没有 `CHANGE_ME`
- [ ] `APP_CRYPTO_DATA_KEY` / `APP_CRYPTO_HASH_PEPPER` 已离线备份
- [ ] 数据库端口没有对公网开放（`ufw status` 无 5432）
- [ ] 应用连的是 `app_rw` 而不是超级用户
- [ ] `flyway_schema_history` 有 V1/V2/V3 且 success
- [ ] HTTPS 正常，http 自动跳转
- [ ] 演示账号（D0231/N0455/N0001/A0001）**在生产库里不存在**
- [ ] 备份任务已跑通，且做过一次恢复演练
- [ ] `X-Robots-Tag: noindex` 生效（病历信息不该被搜索引擎收录）
- [ ] 审计日志有数据（`select count(*) from audit_log;`）
