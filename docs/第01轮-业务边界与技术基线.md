## 三、先把需求重新定义一遍（这是专业视角的第一步）

你的描述里，这个系统的名字叫"医院回访管理系统"，但如果按字面理解成"到点弹个窗提醒医生打电话"，
会严重低估它。它实际上是**四套系统的叠加**：

| 系统本质 | 说明 | 对应你的需求 |
|---|---|---|
| **科室级医疗 CRM** | 管理患者全生命周期档案与联系方式 | "存储几万条病人/医生/病情/联系方式" |
| **临床随访计划引擎** | 按病种/病情自动生成随访时间轴和随访内容 | "张三三个月后复诊、李四三天后取病理报告" |
| **任务调度 + 待办中心** | 把随访计划落成"某护士在某天必须做的某件事" | "匹配后弹出信息提示，让该医务人员记得回访" |
| **多渠道触达网关** | 用 App/短信/微信把消息真正送到人手上 | "推送不同的内容" |

**这四层里，真正的难点是第 2 层和第 4 层，不是第 3 层。**
弹窗是最简单的一步；"这个弹窗该不该弹、弹给谁、弹不出来时怎么办"才是要命的地方。

## 四、需求里 6 个"隐藏难点"（必须现在就说清楚）

### 难点 1：工作人员自助注册 = 病人隐私泄露事故

你写的是"每个人可以下载、注册，由身份选择：工作人员、病人"。

**身份选择这个动作本身必须是受控的，不能是用户自己在下拉框里选。**

原因很直白：如果任何人注册时选"我是主管护士"就能进系统，那他就能看到全科室几万名患者的
姓名、电话、诊断。这不是"可能被滥用"，而是**上线第一天就会出事的级别**。

正确做法：

- **患者**：可以自助注册，但注册后只能看到"绑定到自己就诊记录"的内容；
- **医护**：**不开放自助注册**。由管理员在后台创建账号 → 生成邀请码/一次性激活链接 →
  医护激活并设置密码 → 管理员审核通过后才可登录。工号必须与医院人事口径一致且唯一。

### 难点 2："匹配"这个词，是规则引擎，不是 `if` 判断

你要的"三天后""三个月后"，在真实场景里会迅速膨胀成：

- 胃癌术后：术后 1 个月、3 个月、6 个月、12 个月各一次，且**内容不同**；
- 糖尿病出院：出院后 1 周、1 个月、3 个月，且**要问血糖值**；
- 化疗患者：按**周期**算，不是按固定天数；
- 还有"仅工作日""避开节假日""医生排班冲突顺延"。

所以从一开始就要做成**可配置的随访路径模板（Pathway Template）**，
而不是把天数硬编码在程序里。否则每加一个病种，你就要改一次代码、发一次版。

**这是决定这个系统"能活几年"的最关键的一个设计决策。**

### 难点 3：App 推送在手机上是不可靠的，必须有兜底

现实情况：

- **Android**：App 被"清理后台"后收不到推送（国产 ROM 尤其激进）；
- **iOS**：APNs 可靠，但需要 Apple 开发者账号（99 美元/年）**且需要医院主体资质上架**；
- **微信小程序**：**不能主动推送**，只能用户主动订阅后发"订阅消息"（一次性，用户点一次只能发一次）；
- **短信**：最可靠，但**收费**（约 0.03–0.05 元/条），且需要模板审核。

所以"弹出提醒"这个需求的**工程答案**是：

> **App 内待办列表（永不丢失，打开就有）** + **推送通知（尽力送达）** + **短信（付费兜底，仅对高优先级随访）** + **护士长每日待办汇总（管理兜底）**

只做 App 推送的方案，上线三个月后一定会被投诉"没提醒到"。

### 难点 4：给患者推送"内容"，涉及医疗合规

"根据病情推送不同内容"——如果推送的是**科普/复诊提醒/取报告提醒**，没问题。
如果推送的是**诊断结论、用药调整建议**，性质就变了：这属于诊疗行为，
只有具备互联网医院资质的机构才能做，且需要有资质医师审核留痕。

建议第一版严格限制为：**复诊时间提醒、检查/取报告提醒、通用健康宣教、随访问卷**，
**绝不推送个性化诊疗建议**。这条边界要写进产品需求书。

### 难点 5：电话号码属于敏感个人信息，不能裸存

几万条患者手机号 + 诊断信息放在一个库里，一旦脱库就是重大事件。必须做到：

- 手机号**加密存储**（应用层 AES-256-GCM，密钥与数据库分离），
  列表展示**脱敏**（138****5678），要看完整号码必须二次授权并留审计日志；
- 数据库开启 TDE 或磁盘加密；
- 所有医护账号强制开二次验证（不是可选项）。

### 难点 6："不要出 BUG、稳定运行好几年"靠的是工程制度，不是小心

这句话我特别要正面回答，因为它不是靠"写代码仔细"能达成的。真正的保障手段是：

1. **数据库变更版本化**（Flyway/Liquibase），禁止手工改线上库；
2. **审计表只追加不修改**（append-only），任何改动可追溯；
3. **定时任务幂等**，重复执行不产生重复随访任务；
4. **自动化测试**覆盖核心规则（尤其随访日期推算，这是最容易算错的地方）；
5. **依赖版本锁定**，不追新版本，稳定性优先；
6. **每日自动备份 + 定期恢复演练**（没演练过的备份等于没有备份）。

## 五、合规与资质红线（这一条可能决定项目能不能上线）

### 5.1 硬性法规要求

| 法规 | 对我们的约束 |
|---|---|
| 《网络安全法》《数据安全法》《个人信息保护法》 | 患者数据属敏感个人信息，需单独同意、最小必要、加密存储 |
| 《人口健康信息管理办法（试行）》 | **人口健康信息不得存储在境外服务器**，不得托管在境外云 |
| 《医疗卫生机构网络安全管理办法》（2022） | 医院网络需分级防护，涉及患者数据的系统须做等保 |
| 等级保护 2.0 | 若接入医院内网/与 HIS 对接，通常要求**等保三级**测评 |

**直接推论：不能用 Vercel / Supabase / Firebase / 国外 AWS 等任何境外服务。
服务器必须在中国境内，且最好是医院自有或国内有等保资质的云（阿里云/腾讯云/华为云）。**

### 5.2 我必须在第一轮就告诉你的重大风险：上架

你说"每个人可以下载、注册"。这里有个现实障碍：

> **医疗健康类 App 在国内应用商店上架，需要企业主体 + 相关资质证明。**
> 苹果 App Store 医疗类 App 需要提供医疗执业许可等材料；华为/小米/OPPO/vivo 等国内商店同样严格。
> **个人开发者身份上架医疗类 App 基本不可行。**

微信小程序同理：**医疗类目需要企业主体 + 资质审核**。

所以，"让患者下载 App"这件事，现实中有三条路：

| 路线 | 可行性 | 说明 |
|---|---|---|
| **A. 以医院名义上架**（小程序 + App） | 合规但周期长 | 需要医院配合提供资质，1–3 个月走完流程 |
| **B. 医院内部/定向分发**（APK + H5） | 快，适合先跑通 | 安卓可扫码安装 APK；苹果用 H5/企业签名；无需上架 |
| **C. 先做 H5 + 小程序，不做独立 App** | 推荐起步 | 患者零安装成本，扫码即用，上架压力最小 |

**我的建议：第 1 版走 C + B 组合**（患者端 H5/小程序扫码用，医护端可装 APK），
等院方资质就位后再考虑正式上架。这样今天就能开始开发，不被资质卡住。

## 六、角色与身份模型基线（第 1 版）

```
系统角色
├── 患者（Patient）
│     ├── 自助注册 → 实名/就诊绑定 → 只读自己的随访与宣教
│     └── 填随访问卷、确认复诊、留言咨询
├── 医护（Staff）—— 禁止自助注册
│     ├── 主管医生（Doctor）        可看本人主管患者、制定/调整随访计划
│     ├── 主管护士（Nurse）         可看本人主管患者、执行电话随访、登记结果
│     ├── 护士长 / 科主任（Manager） 本科室全部数据、任务分配与质控统计
│     └── 随访专员（Coordinator，可选）只做电话随访，不看完整病历
├── 系统管理员（Admin）—— 账号、权限、字典、备份，默认不可见患者明细
└── 审计员（Auditor，可选）—— 只看操作日志
```

**关键设计：数据可见性按"主管关系"收敛，而不是按"科室"放开。**
一位护士只应该看到"我是主管护士"的患者，而不是全科室几万人。
这个约束要在**数据库查询层**强制（行级权限 / 数据范围过滤），
不能只在界面上藏起来——界面上藏等于没藏。

| | 方案 A：国内云 SaaS 标准架构 ⭐推荐 | 方案 B：医院内网私有化 | 方案 C：轻量单机 |

**本轮建议先不定死，等你回答下面第 6、7 个问题后再定。**
但无论选哪个，**代码架构完全一致**——这一点很重要，它保证你以后从 C 升到 A/B 时不用重写。

### 为什么用 PostgreSQL 而不是 MySQL

你的场景有大量"时间轴、区间查询、JSON 配置、行级安全"需求：

- 原生 **行级安全策略（RLS）**，正好解决"护士只能看自己主管患者"的问题，且无法被 SQL 绕过；
- **JSONB** 存随访模板配置，灵活且可索引；
- 时间范围查询、分区表、`tstzrange` 类型对"三天后/三个月后"这类需求天然友好；
- 更强的数据一致性与崩溃恢复能力。

MySQL 也完全能用，但对"合规 + 行级权限"这个组合，PostgreSQL 更省事。
**如果你的团队只会 MySQL，也请直说，我按 MySQL 出方案。**

## 八、核心数据模型草案（第 2 轮会细化到字段级）

```
患者域
  patient              患者（含加密手机号）
  patient_contact      联系人/家属（一个患者可有多个）
  encounter            就诊/住院记录（每次住院一条）
  diagnosis            诊断（ICD-10 编码 + 自由文本）

随访域
  followup_template    随访路径模板（按病种，版本化）
  followup_template_item 模板条目（第 N 天/月 + 随访内容 + 执行角色）
  followup_plan        某患者的随访计划（由模板实例化生成）
  followup_task        具体待办任务（谁、何时、做什么、状态）
  followup_record      随访执行记录（电话结果、问卷答案）
  questionnaire        随访问卷模板
  questionnaire_answer 问卷作答

组织与权限域
  department           科室
  staff                医护（工号、职称、角色）
  staff_patient_rel    主管关系（医生/护士 ↔ 患者）★最核心的一张表
  role / permission    角色权限
  user_device          设备与推送 token

系统域
  notification_log     消息发送记录（渠道、状态、回执）
  audit_log            审计日志（只追加）
  sms_record           短信发送与计费记录
  sys_config           系统配置
```

**这张表里，`staff_patient_rel`（主管关系）是整个系统的心脏。**
你说的"指定医务人员，匹配后弹出提示"，本质就是这张表 + 时间条件的一次查询。

## 九、非功能性需求（可量化，第 10 轮写进验收标准）

| 指标 | 目标值 | 说明 |
|---|---|---|
| 容量 | 10 万患者 / 50 万随访任务 | 远超"几万条"，留够 10 年余量 |

| 浏览器/机型 | Chrome/Edge 近两年版本、微信内置、Android 8+ / iOS 14+ | — |

**注意一个反直觉的事实：几万条数据对数据库来说是"几乎不占资源"的量级。**
这个项目真正的成本不在存储和算力，而在**可用性、备份、合规和长期维护**。
所以不要上微服务、不要上 K8s、不要上分库分表——那些只会增加故障点和维护成本，
对一个科室级系统是纯粹的负资产。

## 十二、本轮需要你回答的 10 个问题

> 这 10 个答案会直接决定后面的技术方案。不用写长，简短回答即可。

1. **【最重要】这个系统的最终用途是什么？**
   是给某家真实医院/科室上线服务患者，还是毕业设计/课程作业、亦或个人练手项目？
   （这决定合规路线是"必须过等保"还是"先跑通功能"）

2. **你有医院方面的关系或资质支持吗？**
   例如能否以医院名义申请小程序/备案/上架？（决定走 A 路线还是 C 路线）

3. **工作人员账号**，你同意"不做自助注册，由管理员创建+激活"吗？
   如果不同意，请说明你的场景里为什么需要自助注册。

4. **数据从哪来？**
   (a) 医护手工录入患者信息；
   (b) 从医院 HIS/EMR 系统导出 Excel 再导入；
   (c) 需要和 HIS 系统做实时接口对接（这个难度和周期会大幅上升）。

5. **患者端你希望是什么形态？**
   微信小程序 / 安卓 APK / 苹果 App / 手机浏览器网页（H5），可以多选，并说明优先级。

6. **消息渠道你能接受哪些？**
   是否愿意为短信付费（约 0.04 元/条）？医院是否已有微信公众号/服务号？

7. **服务器你倾向于哪种？**
   国内公有云（阿里/腾讯/华为）、医院内网机房、还是先用你自己的电脑/一台小服务器试跑？
   你手上现在有没有已购的服务器或域名？

8. **预算范围**大概是多少？（服务器 + 短信 + 备案等，不含人力）

9. **开发与维护由谁做？**
   只有你一个人吗？有没有其他人参与开发或后续运维？这会影响我给出的文档详细程度和自动化程度。

10. **能否提供你们科室真实的随访流程样例？**
    例如："胃癌根治术患者，出院后 1 个月电话随访，3 个月返院复查胃镜，6 个月……"
    有三五个真实例子，我做出来的规则引擎才会贴合实际，而不是纸上谈兵。
