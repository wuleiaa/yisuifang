| 项目 | 费用 |
|---|---|

**在你的 200–300 元预算内，还能剩下一半。**

### 1.4 买之前必须做的两件事

**第一件：看清楚"续费价格"。**

```
首年促销价  99 元      <- 你看到的
次年续费价  1500 元    <- 你没看到的（警告）
```

这是云厂商最常见的手法。演示期按月付就不存在这个问题；
如果将来要长期用云，务必先算清三年总成本，或者干脆部署到医院内网。

**第二件：确认是否需要备案。**

| 访问方式 | 是否要备案 | 能否跑微信小程序 |
|---|---|---|
| 域名（followup.example.com） | **必须 ICP 备案**，2–3 周 | 可以 |
| 纯 IP 地址 | 不需要 | **不行**（小程序不支持 IP） |

**结论**：演示阶段如果只给自己和院领导看，用 IP + HTTP 就能跑；
但要演示**微信小程序**，就必须有备案域名。

**所以备案这件事，建议你今天就去启动**——它不花钱，只是耗时间。

## 二、正式上线的两个方案

### 方案 A：部署到医院内网（推荐）

```
             互联网
                |
         医院公网出口
                |  （信息科配置端口映射 / 反向代理）
         +------v-------+
         | Nginx (HTTPS)|  <- DMZ 区
         +------+-------+
                |
    ======== 医院内网 ========
                |
    +-----------v------------+
    |  虚拟机 4核8G           |
    |  |- 随访系统 (Java)     |
    |  |- PostgreSQL 16      |
    |  +- Redis 7            |
    +------------------------+
```

| 优点 | 缺点 |
|---|---|
| 数据不出医院，合规等级最高 | 需要信息科配合（流程 1–3 个月） |
| 医院零额外采购成本 | 需要走等保测评（3–8 万，医院承担） |
| 不受云厂商续费涨价影响 | 需要医院有公网出口和域名 |
| 备份可直接用医院 NAS | 出故障时依赖医院 IT 响应 |

**需要向信息科提的需求清单**（就这几条）：

1. 一台虚拟机：4 核 8G，100GB 磁盘，Linux；
2. 一个内网 IP；
3. 一个公网出口：把 `随访域名:443` 反向代理到这台虚拟机的 8080 端口；
4. 一个子域名（如 `suifang.hospital.com`）；
5. 数据库端口**不需要**对外开放。

**第 3 条是唯一需要信息科"开个口子"的地方。**
跟他们说"只开放 443 端口、只转发到内网一台机器"，风险很小，通常能批。

### 方案 B：公有云单机部署（备选）

| 优点 | 缺点 |
|---|---|
| 立刻能上线，不依赖任何人 | 数据在医院外部，部分医院不接受 |
| 运维简单，有控制台 | 续费涨价，三年下来不便宜 |
| 可随时扩容 | 需做等保二级（约 3–5 万） |

**如果信息科流程走不动，可以先上公有云，等流程走通再迁回内网。**
架构上我会保证：**迁移只需要导数据 + 改配置，不需要改代码。**

### 2.1 为什么两个方案用同一套部署方式

因为都是 `Docker Compose` 单机部署，配置文件完全一样，
区别只是"跑在医院虚拟机上"还是"跑在云服务器上"。

**这是刻意的设计**：让你今天在云上演示，明天能原样搬进医院内网。

## 三、容量测算（确认 4 核 8G 够用）

按一个科室、4 年、10 万患者估算：

| 组件 | 内存占用 | 说明 |
|---|---|---|
| 操作系统 + Docker | 约 500 MB | |
| PostgreSQL | 约 700 MB | `shared_buffers = 512MB` |
| Redis | 约 200 MB | `maxmemory 256mb` |
| 随访系统（JVM） | 约 1.4 GB | `-Xmx1024m` + 元空间 + 线程栈 |
| Nginx | 约 50 MB | |
| **合计** | **约 2.9 GB** | **4G 宽裕，2G 紧张但能跑** |

| 资源 | 使用量 | 备注 |
|---|---|---|
| 磁盘 | 约 15 GB | 数据库 8GB + 备份 5GB + 系统 2GB |
| CPU | 峰值 < 50% | 100 并发医护足够 |

**结论：2 核 4G 是演示的下限，4 核 8G 是正式上线的舒适配置。**

```
你本机：   JDK 24      <- 短期版本，只维护 6 个月
生产要求： JDK 21 LTS  <- 维护到 2031 年
```

**这不是小事**：用 24 开发、用 21 部署，可能出现"本地能跑、服务器报错"。

你本机没有 Docker。装 Docker Desktop 有两个注意点：

1. **Windows 家庭版**需要 WSL2 后端，安装时按提示装即可；
2. Docker Desktop 体积较大（约 1–2 GB），但**它是这个项目最省事的选择**——
   装好后一句 `docker compose up` 就能把 PostgreSQL + Redis 拉起来，
   不用手工装数据库、配环境、建用户。

**替代方案**（不想装 Docker）：直接装 PostgreSQL 16 的 Windows 安装包，手工建库。

## 五、部署架构（Docker Compose）

### 5.1 服务清单

```
docker compose 一次启动 5 个服务

  +----------------------------------------+
  |  nginx        :80 :443   反向代理 + SSL |
  |    |                                    |
  |  app          :8080      随访系统后端   |
  |    |                                    |
  |  postgres     :5432      主数据库       |
  |  redis        :6379      缓存与队列     |
  |  backup       定时任务    每日备份      |
  +----------------------------------------+

  只有 nginx 对外暴露端口，其余服务只在 Docker 内网可见。
```

### 5.2 交付的配置文件

见 [deploy/docker-compose.yml](deploy/docker-compose.yml) 与
[deploy/.env.example](deploy/.env.example)。

**配置里已经处理好的几个安全问题**：

| 问题 | 处理方式 |
|---|---|
| 数据库端口暴露到公网 | 不映射端口，只在 Docker 内网可见 |
| 数据库用超级用户连接 | 应用使用 `app_rw`（第 6 轮铁律） |
| 密码写在配置文件里 | 全部走 `.env`，`.env` 加入 `.gitignore` |
| 容器以 root 运行 | 指定非 root 用户 |
| 日志无限增长 | Docker 日志轮转（单文件 10MB，保留 3 个） |
| 数据库时区不对 | 显式设置 `TZ=Asia/Shanghai` |

## 六、域名与备案流程

### 6.1 流程（越早启动越好）

```
1. 注册域名（10 分钟，29-70 元/年）
2. 实名认证（1-3 天）
3. 购买服务器（中国境内，剩余时长 >= 3 个月）
4. 提交 ICP 备案（云厂商控制台，免费）
5. 云厂商初审 + 管局审核（合计 2-3 周）
6. 备案通过 -> 域名解析 -> 配 SSL 证书
```

### 6.2 关于备案主体的重要提醒

> **微信小程序的服务器域名必须备案，且备案主体需与小程序主体一致或有合法关联。**

这意味着：

- 小程序用 **医院主体** 注册 → 域名也必须用**医院主体**备案；
- 个人备案的域名**不能**用于医院的正式小程序。

**所以：**

- **演示阶段**：可以用你自己的个人域名 + 云服务器（只给自己和院领导看）；
- **正式上线**：必须由医院提供主体，走医院备案。

**请尽快向科室主任/信息科确认：能不能用医院名义注册小程序和备案域名。**
这是全项目周期最长的一环（1–3 个月），越早启动越好。

## 七、部署检查清单（每次部署必看）

> 这份清单是从前面的实测里总结出来的，每条都对应一个真实踩过的坑。

### 7.1 部署前

- [ ] `.env` 文件已生成，密钥是随机生成的（不是默认值）
- [ ] `.env` 已加入 `.gitignore`，**没有被提交到 Git**
- [ ] 数据库账号是 `app_rw`，**不是 `postgres`**
- [ ] 服务器时区设为 `Asia/Shanghai`
- [ ] 磁盘剩余空间 > 30GB
- [ ] 域名已备案（若用域名访问）
- [ ] SSL 证书已配置且能自动续期

### 7.2 部署后（逐条执行，缺一不可）

**第 1 条最容易忽略、后果最严重：**

- [ ] **确认数据库连接不是超级用户**

```bash
docker compose exec postgres psql -U app_rw -d followup -c \
  "SELECT current_user, (SELECT rolsuper FROM pg_roles WHERE rolname=current_user);"

# 期望输出：app_rw | f
# 如果输出 t（超级用户），说明行级权限完全失效，必须立刻修正！
```

- [ ] 运行冒烟测试，确认病理闸门和行级权限生效

```bash
docker compose exec -T postgres psql -U app_rw -d followup < tools/db_smoke_test.sql
# 期望：全部 PASS，0 条 FAIL
```

- [ ] 确认 PostgreSQL 端口**没有**对公网开放

```bash
# 从你自己的电脑执行，期望"连接超时/被拒绝"，而不是"连接成功"
telnet <服务器IP> 5432
```

- [ ] 确认 HTTPS 证书有效（浏览器地址栏有小锁）
- [ ] 确认 HTTP 自动跳转到 HTTPS
- [ ] 备份任务已生效（检查备份文件是否生成）

```bash
docker compose exec backup ls -lh /backup
```

- [ ] **做一次恢复演练**（最容易跳过，也最重要）

```bash
docker compose exec postgres createdb -U postgres restore_test
docker compose exec postgres pg_restore -U postgres -d restore_test /backup/latest.dump
# 能恢复成功 = 备份有效；报错 = 备份是假的，等于没有备份
```

### 7.3 上线后第一周

- [ ] 每天检查一次应用日志，确认没有异常堆栈
- [ ] 确认定时任务按小时执行（看 `notify_log` 有没有数据）
- [ ] 确认提醒确实发到了医护手机上（找一位医生实际验证）
- [ ] 确认患者小程序能看到自己的随访计划
- [ ] 找一个真实病例从头走一遍完整流程

## 十一、本轮需要你回答的问题（3 个）

1. **能不能用医院名义注册小程序 + 备案域名？**
   这是全项目周期最长的一环（1–3 个月），**建议你现在就问科室主任**。

   （a）能给虚拟机 + 开公网端口；（b）只能给内网虚拟机，不能对公网；

   我建议分三步走，你选一个节奏：

   | 节奏 | 时间 | 交付什么 |
   |---|---|---|
   | 快速验证 | 约 1 周 | 能登录、能看患者列表、能录入回访记录（跑通主流程） |
   | 标准 | 约 3–4 周 | 加上随访路径自动生成、病理闭环、提醒推送 |
   | 完整 | 约 8–10 周 | 加上质控看板、Excel 导入、审计、完整测试 |

   **我建议先走"快速验证"**：让你和科室用真实数据摸一摸，再根据反馈调整，
   比我闷头做完整版更靠谱。
