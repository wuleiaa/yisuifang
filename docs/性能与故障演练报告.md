# 性能压测与故障演练报告

> 日期：2026-09-18　环境：开发机（2 核 / 数据库与应用同机 / PostgreSQL 16.10 / JDK 21）
> 工具：`tools/load-test.mjs`（压测）、`tools/fault-drill.mjs`（故障演练）、
> `tools/drill-db-outage.ps1`（数据库中断演练）

---

## 一、性能压测

### 1.1 验收场景（第 10 轮定的标准：并发 20、P95 < 300ms、失败率 0%）

| 数据规模 | 吞吐 | P50 | P95 | P99 | 失败率 | 结论 |
|---|---|---|---|---|---|---|
| 3 位患者 / 10 个任务 | 835 req/s | 22ms | 37ms | 53ms | 0% | 通过 |
| **1000 位患者 / 6010 个任务** | 315 req/s | 45ms | 168ms | 239ms | 0% | **通过** |

真实科室的并发量是 10–30 人，该配置余量约 30 倍。

### 1.2 加压找拐点

| 并发 | 吞吐 | P95 | 失败率 |
|---|---|---|---|
| 20 | 835 req/s | 37ms | 0% |
| 50 | 914 req/s | 65ms | 0% |
| 150 | 909 req/s | 181ms | 0% |

**吞吐在约 900 req/s 处饱和，但延迟只是上升、不报错**——过载时表现是"变慢"而不是"崩掉"，
这对医疗系统是更可接受的失败方式。

### 1.3 数据量增长的真相

数据从 3 位患者涨到 1000 位患者后，吞吐从 835 掉到 315 req/s（2.6 倍），
最慢的是"待办列表"（P95 214ms）。

用 `tools/explain-hot-queries.sql` 看执行计划，结论是：
LIMIT 100 之前需要先把该医生名下 **3005 条**任务取回并排序，
即"取回全部再截断"。已加 V3 索引优化过滤路径（`idx_task_assignee_status_due` 等）。

> 复测后 P95 变化在噪声范围内——**瓶颈不在索引，而在单机 CPU**：
> 应用、数据库、压测器共用一个 2 核 CPU。生产环境应用与数据库分开后此瓶颈自然消失。

### 1.4 连接池调优实测（重要，别凭感觉调大）

1000 位患者、20 并发下：

| 连接池 | P50 | P95 | P99 | 最大 |
|---|---|---|---|---|
| **10（默认）** | 43ms | 169ms | 225ms | 399ms |
| 20 | 31ms | 200ms | **632ms** | **2883ms** |

**连接数调大只是把排队从应用内挪到了数据库侧**：中位延迟变好，尾部延迟明显恶化。
对"护士打电话"这种场景，P95/P99 比 P50 更重要，因此默认保持 10。
（经验值：`pool ≈ CPU 核数 × 2~4`，且给数据库 `max_connections` 留余量。）

## 二、故障演练结果

`node tools/fault-drill.mjs` —— **13 项全部通过**（修复后）。

### 2.1 发现并修复的两个真问题

#### 问题 1：并发抢锁完全失效（严重）

**现象**：20 个并发请求抢同一个任务，**18 个都"抢到了"**。

**根因**：`claim()` 是"先查出来判断有没有被占，再保存"。
两个请求同时进来都会读到"没被占用"，然后都写入成功。
也就是说——**两位护士同时点"立即回访"，两人都会以为自己拿到了这通电话**，
防重复拨打的设计形同虚设。

**修复**：把判断与写入合成一条带条件的原子 `UPDATE`（`TaskService.tryLock`），
由数据库保证只有一个事务能更新成功。同时 `complete()` 也改用同一把锁，
避免并发提交产生两条回访记录。

**验证**：修复后 20 并发下只有 1 个用户能拿到锁，其余全部收到
"该任务正在被其他同事处理"。同时保留"同一人重复打开任务不报错"的幂等性。

> 附带踩坑：原子更新是原生 SQL，绕过了 Hibernate 一级缓存，
> 导致"领取成功但状态仍显示 PENDING"。已在更新后清理缓存（`em.clear()`）。

#### 问题 2：参数类型错误返回 500

**现象**：`/api/tasks/todo?days=abc` 返回 HTTP 500。

**根因**：Spring 的参数类型转换异常落到了"系统异常"分支。
调用方传错参数却被当成服务端故障，日志里还会刷 ERROR 级堆栈。

**修复**：`GlobalExceptionHandler` 增加对参数类型/格式/缺失、请求体不可读、
方法不支持的处理，统一返回 400 / 405。

### 2.2 通过的检查项

| 检查 | 结果 |
|---|---|
| 并发抢锁不会两人同时拿到 | 通过（修复后） |
| 同一任务重复提交被拒 | 通过 |
| 搜索框输入 SQL 注入串（4 种）不报错、不泄露、不拖慢 | 通过 |
| 参数乱填（5 种边界）不会 500 | 通过（修复后） |
| 5000 字超长结论被校验拦下 | 通过 |
| 缺少必填字段被拦下 | 通过 |
| 无令牌 / 伪造令牌 / 篡改令牌 被拒 | 通过 |
| 患者令牌不能调医护接口，反之亦然 | 通过 |
| 越权查看患者、越权建账号 被拒 | 通过 |

### 2.3 数据库中断演练（`tools/drill-db-outage.ps1`）

| 步骤 | 结果 |
|---|---|
| 停掉数据库后调用接口 | HTTP 500 + "系统繁忙，请稍后再试"，**10 秒返回，线程没有被堵死** |
| 重启数据库后再次调用 | **自动恢复，无需重启后端** |

**改进**：10 秒是连接池等待超时，用户盯着转圈太久，已把
`connection-timeout` 从 10s 调到 5s（可配置 `DB_CONN_TIMEOUT_MS`）。

## 三、遗留与建议

| 项 | 说明 |
|---|---|
| 单机吞吐上限约 900 req/s | 生产环境把数据库独立部署后可解除 |
| 待办查询"取回全部再截断" | 数据量到十万级任务时需改写（先按索引排序取 100 条） |
| 患者端验证码存单机内存 | **多实例部署前必须换 Redis**，否则验证码会随机失效 |
| 定时提醒、病理闭环等阶段二功能 | 尚未开发，压测未覆盖 |
