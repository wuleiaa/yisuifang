## 二、病理报告闭环设计（本轮最重要）

### 2.1 先说风险：为什么"结论录入即对患者可见"不能这么做

你的需求是"结论出来后录入系统，能让患者看到"。**功能方向完全正确**，
但如果做成"护士录入 → 患者立刻在小程序看到"，会有三个严重问题：

**问题一：恶性结果由系统告知患者，是重大医疗风险。**

想象这个场景：患者在家刷手机，突然看到"（结肠）腺癌"四个字，
没有任何医生在场解释。患者可能出现严重心理应激，甚至引发医疗纠纷。
**告知坏消息必须由医生完成，这是临床规范，不能让一个 APP 代劳。**

**问题二：病理结论有"最终"和"初步"之分。**

有些报告会写"待免疫组化进一步明确"，或者需要加做检测才能定性。
如果患者的手机同时看到"（初步）"和"（最终）"两个版本，
就会出现"昨天说不是癌，今天说是癌"的情况。

**问题三：原始病理报告是给医生看的。**

报告里有大量专业术语、分级、切缘情况、免疫组化指标。
直接原样展示给患者，患者看不懂反而会更焦虑，还会拿着报告到处问。

### 2.2 正确方案：病理报告状态机

我设计成一条**带闸门的流水线**，每一关都要有人负责：

```
① 待录入
     │  护士/医生录入结论摘要（可上传 PDF）
     ▼
② 待医生审核          ← 护士录完后，医生端出现待办
     │  主管医生核对内容准确性
     ▼
③ 医生审核通过
     │
     ├───【低风险：良性/炎症/增生】──────────────┐
     │                                            │
     └───【高风险：高级别瘤变/癌/可疑恶性】        │
              │                                   │
              │  ★ 强制闸门：医生必须勾选        │
              │    "已电话/当面告知患者本人"      │
              │    并填写告知时间                │
              ▼                                   │
        ④ 对患者可见 ◄────────────────────────────┘
              │
              │  系统自动通知患者（小程序订阅消息 + 打开可见）
              ▼
        ⑤ 患者已读（记录已读时间）
              │
              ├─ 患者选择"来院领取纸质版" → 生成领取凭证
              │         ▼
              │    ⑥ 领取登记（谁发的、何时发的、患者签字/扫码确认）
              │
              └─ 若病理为恶性 → 自动触发肿瘤随访路径（见 2.4）
```

**核心规则：**

| 规则 | 说明 |
|---|---|
| 护士可录入，**不可发布** | 录入后进入"待医生审核"，患者看不到 |
| 医生审核通过才能发布 | 低风险直接通知患者 |
| **高风险必须"已告知"才能发布** | 系统强制勾选，防止"系统代替医生通知癌症" |
| 报告有版本 | 初步报告和最终报告分别记录，患者只看到最新已发布版本 |
| 患者可见的是**摘要**，不是原始报告 | 医生填写"通俗解读"（如"良性息肉，建议 6-12 个月复查"） |
| 原始 PDF 可选开放 | 默认关闭，医生可手动开放某份报告 |
| 所有查看留有记录 | 谁何时查看、发布、修改，全部进审计日志 |

### 2.3 给患者的界面长什么样

```
┌─────────────────────────────────┐
│  病理报告                        │
│                                  │
│  检查项目：结肠镜 + 活检          │
│  报告日期：2026-10-06            │
│  状态：✅ 已出报告                │
│                                  │
│  ┌───────────────────────────┐  │
│  │ 医生解读                   │  │
│  │                           │  │
│  │ 本次切除的是良性息肉，      │  │
│  │ 局部有轻度不典型增生，      │  │
│  │ 已经完整切除，无需额外治疗。│  │
│  │ 建议 6-12 个月复查一次肠镜。│  │
│  │                           │  │
│  │  —— 李医生  2026-10-07    │  │
│  └───────────────────────────┘  │
│                                  │
│  [ 查看原始报告 PDF ]  ← 可选    │
│                                  │
│  [ 预约来院领取纸质报告 ]         │
└─────────────────────────────────┘
```

**注意："医生解读"这一段是必填项，不是选填。**
这是系统对患者负责的关键——患者看到的第一句话必须是医生写的白话解释，
而不是一串病理术语。

### 2.4 架构级发现：规则引擎必须支持三种触发器

你的病理需求暴露了一个重要事实——**随访任务不只由时间产生**：

| 触发器类型 | 例子 | 产生方式 |
|---|---|---|
| **时间型** | 术后 3 天电话回访、术后 1 个月复诊 | 按手术日期 + 偏移天数计算 |
| **事件型** | 病理报告出来后通知患者 | 由业务动作触发（报告发布） |
| **条件型** | 病理为恶性 → 转入肿瘤随访路径 | 由结果值分支 |

**第 2 轮我按纯时间型设计是不够的，本轮升级为三触发器模型。**
这三条都要在规则引擎里实现，否则"病理出来后通知患者"这个需求根本落不了地。

## 三、"未回访就重复提醒"——升级为催办链路

你明确说了：**医生未进行回访，消息会重复提醒，不自动顺延、不自动转交。**
这个决策我认同（自动顺延会让随访变成"永远推迟"）。

但单纯的"重复提醒"如果只提醒医生本人，遇到医生休假一周的情况就会一直无效。
所以我把它做成**逐级升级的催办链路**：

### 3.1 催办时间线（可配置）

| 阶段 | 触发条件 | 提醒对象 | 方式 |
|---|---|---|---|
| T+0 | 到达随访时间点 | **主管医生** | App 弹窗 + 企业微信消息 |
| T+2 小时 | 仍未处理 | 主管医生 | 再次弹窗（这次带"已逾期"标记） |
| T+ 当天 17:00 | 当天仍未处理 | 主管医生 **+ 搭档护士** | 双方都收到提醒（搭档可代为执行） |
| T+24 小时 | 仍未处理 | 主管医生 + 搭档护士 + **护士长** | 升级 |
| T+72 小时 | 仍未处理 | 以上全部 + **科主任** | 红色告警，进入科室质控看板 |

**这个设计的妙处**：医生休假时不需要任何人手工操作，
护士看到"搭档未回访"的提醒后可以直接代为完成（系统记录实际执行人是护士），
护士长在 24 小时后介入分配。**系统自动兜底，不依赖人工盯。**

### 3.2 长期离岗怎么办（补充场景）

你说的"重复提醒"覆盖了短期情况。但如果医生**进修 3 个月或调离科室**，
让任务一直红着也不合理。所以补两个功能：

| 功能 | 谁可用 | 效果 |
|---|---|---|
| **指定代理人** | 医生本人 | 离岗期间我的任务自动通知代理人 |
| **批量改派** | 护士长/科主任 | 把某医生的未完成任务批量转给另一人 |

操作留审计日志，谁改派给谁、什么时候、什么原因，全部可追溯。

### 3.3 "医生和护士是搭档"——数据模型怎么表达

这句话非常关键，它决定了整个权限模型：

```
医护搭档组（Care Team）
├── 组员：1 名主管医生 + 1 名主管护士（可多名）
├── 服务的患者：由住院时手工指定关联
└── 随访任务：挂到"组"上，而不是挂到"某个人"上
```

**任务挂到组上，好处有三个：**

1. 医生休假时，护士天然能看到并处理，不需要系统做复杂的转交逻辑；
2. 医生轮转调岗时，只需调整组员，任务不用一条条改；
3. 权责清晰——任务永远属于这个组，执行人是谁单独记录。

这就是你第 2 轮问的"医生轮转调岗怎么处理"的答案：
**不动任务，动组员。**

## 四、iOS 弹不了窗怎么办——有三个更好的方案

你问的是："弹不了窗，如何提醒呢？还有其他方案？"

**有，而且有一个方案几乎完美解决了这个问题。**

### 4.1 ★ 首选方案：企业微信自建应用（推荐）

三甲医院基本都在用**企业微信**（或可以免费开通）。企业微信允许医院创建一个**自建应用**，
我们的系统通过接口把随访提醒推到医护的企业微信里。

**为什么这是最优解：**

| 优势 | 说明 |
|---|---|
| **iOS 也能可靠推送** | 企业微信是腾讯自家 App，系统不会杀后台，iOS 通知栏正常弹 |
| **安卓也可靠** | 小米/华为/OPPO/vivo 都对微信/企业微信做白名单，比自研 App 稳定得多 |
| **完全免费** | 企业微信免费版就支持自建应用，一个科室几十人绰绰有余 |
| **不用装新 App** | 医护本来就在用，推广成本几乎为零 |
| **可以绑微信接收** | 不装企业微信也能通过微信接收（微信插件功能） |
| **医院信息科认可** | 企业微信本身是合规产品，比自研 App 更容易通过审核 |
| **能点进我们的系统** | 消息里可以带链接，直接跳到随访 H5 页面填结果 |

**唯一的前提条件**：需要医院企业微信管理员（通常是信息科）创建一个自建应用，
并给我们 `企业ID`、`应用 Secret`、`应用 AgentID` 三个参数。
**这三个参数不需要任何开发工作，信息科 10 分钟就能配好。**

### 4.2 备选方案：微信服务号订阅通知

医院已有公众号。如果是**服务号**（认证过的三甲医院公众号基本都是），可以用订阅通知推送。

| 优点 | 缺点 |
|---|---|
| 免费 | 需要用户主动订阅，用户不点订阅就发不出去 |
| 已在患者/医护微信里 | 一次性订阅：订一次只能发一条；长期订阅审核较严 |

**适合作为补充渠道**，不适合作为唯一渠道。

### 4.3 兜底方案：短信，但只在升级时发

你说短信太贵。这个顾虑在**每条都发**的前提下是对的，但我们改一下策略：

> **只在任务逾期 24 小时且升级到护士长时，才发一条短信。**

算一笔账：一个科室假设每月产生 300 条随访任务，其中逾期需要升级的按 5% 算 = 15 条。
15 条 × 0.045 元 = **每月 0.68 元，一年 8 元**。

**这个成本完全可以接受，而且它保证了"最坏情况下一定有人知道"。**
我建议把这一条留作可选项，等你和科室确认后再决定是否开启。

### 4.4 四层提醒矩阵（最终方案）

| 层级 | 渠道 | 费用 | 可靠性 | 覆盖端 |
|---|---|---|---|---|
| 第 1 层 | **App 内待办列表** | 0 | **100%（权威数据源）** | 全部 |
| 第 2 层 | **企业微信应用消息** | 0 | 高 | iOS + 安卓 |
| 第 3 层 | 微信服务号订阅通知 | 0 | 中 | iOS + 安卓 |
| 第 4 层 | 短信（仅升级时） | 约 8 元/年 | 极高 | 全部 |

**这个矩阵的意思是**：即使前 3 层全部失效（用户关了通知、没订阅、企业微信没装），
第 1 层的待办列表依然完整——打开 App 或网页就能看到所有待办。
而第 4 层保证极端情况下也有兜底。

**结论：iOS 弹不了窗的问题，用企业微信解决了。医护端甚至可以不做独立 App。**

### 4.5 那么医护端还需要安卓 APK 吗？

需要，但定位变了：

| 端 | 定位 |
|---|---|
| 企业微信（H5 应用） | **日常提醒与快速处理的主力** |
| 安卓 APK | 需要离线、需要大量录入、需要拍照上传时的增强端 |
| 手机浏览器网页 | 兜底，任何设备都能用 |
| 电脑网页（管理后台） | 护士长/主任做统计、批量操作、导入导出 |

**好消息：这三个端用的是同一套 uni-app 代码，我写一遍就行。**

护士长做质控、医院做检查、出现纠纷时查证，全靠这张表。

## 六、存储容量重算（加入病理报告文件后）

第 2 轮我算的是纯数据库 8 GB，**但病理报告 PDF 改变了这个数**：

| 项目 | 计算 | 占用 |
|---|---|---|
| 病理报告 PDF | 2 万份 × 500 KB | **10 GB** |
| 检查图片（若上传） | 按需，保守估 | 5–20 GB |
| 数据库 | 第 2 轮测算 | 8 GB |
| 备份（保留 30 天，压缩后约 1/3） | — | 约 10 GB |
| **合计** | | **约 33–48 GB** |

### 6.1 这意味着什么

- **云服务器 60 GB 系统盘：不够用**，会越来越紧张；
- **医院内网部署：用 NAS 或存储服务器，完全不是问题**（这也是我第 2 轮推荐内网的原因之一）；
- **如果必须在云上**，需要挂载对象存储（约 0.12 元/GB/月）：
  50 GB ≈ 6 元/月 ≈ **72 元/年**。这个费用可接受。

### 6.2 文件存储的几条硬规矩

| 规矩 | 原因 |
|---|---|
| 文件**不存数据库**，只存路径和校验值（SHA-256） | 数据库存大文件会严重拖慢备份和查询 |
| 文件名**不用患者姓名** | 防止通过文件名泄露信息 |
| 存储路径**不可猜**（UUID 目录） | 防止遍历下载他人报告 |
| 下载**必须走后端鉴权**，不用公开 URL | 防止链接被转发 |
| 所有 PDF **打水印**（患者姓名 + 查看时间） | 泄露时可追溯来源 |
| 文件访问**全部记审计日志** | 谁下载了什么，必须可查 |

## 九、本轮需要你回答的问题（6 个）

1. **企业微信**：医院现在用企业微信吗？
   能否请信息科创建一个自建应用并给你三个参数（企业ID、Secret、AgentID）？
   如果医院不用企业微信，是否愿意申请一个（免费）？
   **这一条直接决定 iOS 端的提醒方案能不能落地，是本轮最关键的问题。**

2. **病理报告的"医生审核"由谁做？**
   是主管医生本人，还是病理科医生？如果需要病理科参与，流程会复杂一些，请说明。

3. **"已告知患者"这个闸门，你认同吗？**
   如果科室觉得太麻烦，可以退一步：只对"恶性/可疑恶性"强制，良性不强制。你倾向哪种？

4. **病理报告 PDF 要上传到系统吗？**
   还是只录入文字结论就够？这直接影响存储需求和开发工作量。

5. **催办升级的时间点**（2小时/当天17:00/24小时/72小时）是否符合你们科室的工作节奏？
   比如你们是不是 17:30 下班，或者下午门诊特别忙不方便回访？

6. **患者看报告的实名验证**要做到什么程度？
   (a) 手机号 + 短信验证码（每次登录）、(b) 手机号 + 首次设置密码、
   (c) 微信一键登录（最方便，但换手机号会失联）。
   我建议 (b) + 微信绑定，兼顾安全和便利。
