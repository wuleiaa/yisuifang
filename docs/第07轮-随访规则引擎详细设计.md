## 一、先修一个 bug：多路径并行的 schema 缺陷

你说"需要两条路径并行"，这句话**直接暴露了我第 6 轮设计里的一个错误**。

第 6 轮我写了这条约束：

```sql
-- 旧：一次住院只能有一条未关闭的随访计划
CREATE UNIQUE INDEX uk_plan_encounter ON followup_plan(encounter_id) WHERE status <> 'CLOSED';
```

**这条约束会让"胆总管结石 + 胆囊结石"两条路径根本建不起来**——
第二条计划会被数据库直接拒绝，报"唯一约束冲突"。

而且这个错误很隐蔽：单条路径的场景测试完全正常，只有遇到复合病种才会暴露，
很可能要等到科室真实使用几个月后才发现。

### 修正后的约束

```sql
-- 新：同一次住院可以有多条未关闭计划（不同模板），但同一模板不能重复生成
CREATE UNIQUE INDEX uk_plan_enc_tpl ON followup_plan(encounter_id, template_id)
    WHERE status <> 'CLOSED' AND template_id IS NOT NULL;
```

**效果**：

| 场景 | 旧约束 | 新约束 |
|---|---|---|
| 胆总管结石 + 胆囊结石（两条不同路径） | 被拒绝 | 允许 |
| 同一条路径生成两次（重复执行调度） | 被拒绝 | 仍然被拒绝（防重复） |
| 手工创建的无模板计划 | 允许多条 | 允许多条 |

同时新增 `pathway_label` 字段，让界面能直接显示"这条路是治什么"：

```
患者：李某某  住院号 2026****3721
├─ 路径 1：胆总管结石（ERCP 取石术后）      3 条待办
└─ 路径 2：胆囊结石（腹腔镜胆囊切除术后）   5 条待办
```

### 实测验证

```
parallel_plans = 2
pathways = 胆总管结石（ERCP 取石术后） | 胆囊结石（腹腔镜胆囊切除术后）

PASS 4.2 已拦截同一模板重复生成
        -> duplicate key value violates unique constraint "uk_plan_enc_tpl"
```

**这是本轮最有价值的一次修正。** 再次说明早期做真实场景测试的必要性——
如果等到开发完成才发现，就要动数据库、改代码、重新测试。

## 二、服务号不做之后：确立"零依赖原则"

你说第一版独自开发，服务号模板申请不了。这带来一个重要的设计原则。

### 2.1 问题：哪些功能需要"求人"才能用

| 渠道 | 依赖什么 | 独自开发能做吗 |
|---|---|---|
| App 内待办列表 | 无 | 能 |
| 安卓本地定时通知 | 无（系统能力） | 能 |
| 开屏强制提醒 | 无 | 能 |
| 小程序订阅消息 | 小程序主体 + 备案 + 类目审核 | 用**测试号**能开发，正式上线需医院主体 |
| 服务号订阅通知 | 服务号 + 模板审核 | 第一版不做 |
| 企业微信 | 信息科创建自建应用 | 第二期 |
| 短信 | 付费 + 模板审核 | 暂不做 |

### 2.2 所以确立这条原则

> **零依赖原则：核心提醒能力必须完全不依赖任何外部审批，开箱即用。**
>
> 第 1 层（待办列表）+ 第 2 层（安卓本地通知）+ 第 5 层（开屏强制提醒）
> 构成**不可关闭的提醒闭环**。其余的订阅消息、服务号、企业微信、短信
> 都是"锦上添花"的增强层——**有更好，没有也不影响系统可用**。

### 2.3 具体落地

| 阶段 | 用到的渠道 | 需要谁配合 |
|---|---|---|
| **现在（独自开发）** | 待办列表 + 安卓本地通知 + 开屏提醒 + 小程序**测试号** | 无 |
| **演示给院领导** | 同上 | 无 |
| **医院提供主体后** | 增加小程序订阅消息（正式） | 信息科/宣传科 |
| **后续** | 服务号订阅通知、企业微信、短信 | 按需推进 |

**微信小程序测试号**（个人即可免费申请）支持订阅消息的**测试模板**，
足够把功能开发和演示跑通。等医院的正式小程序批下来，
只需要把 appid 换成正式的、模板 ID 换成正式模板，**代码一行不用改**。

我在代码里会把这层做成配置项，切换时改配置即可。

## 三、规则引擎总体数据流

从患者出院到随访完成，数据是这样流动的：

```
① 数据进入
   护士录入 / Excel 导入
   → patient + encounter + diagnosis + medical_procedure
        ▼
② 路径匹配（自动 + 人工兜底）
   出院诊断 / 手术名称 / ICD → template_match_rule
   ├─ 命中 1 条 → 自动选用
   ├─ 命中多条 → 提示护士选择（可多选 → 多路径并行）
   └─ 命中 0 条 → 进入「待指定路径」列表
        ▼
③ 计划实例化
   确定时间锚点 → 生成 followup_plan（每个模板一条）
        ▼
④ 任务生成
   遍历模板条目 → 求值分支条件 → 计算 due_at → 生成 task
   幂等：ON CONFLICT DO NOTHING
        ▼
⑤ 事件补生成（运行中）
   病理报告发布 / HP 结果录入 / 计划调整
   → 重新扫描计划 → 补生成条件型任务
        ▼
⑥ 提醒调度（每小时）
   T-1 预告 → T 日每 2 小时催办 → 逾期降频 → 夜间免打扰
        ▼
⑦ 执行与记录
   锁定任务 → 打电话 → 填表单 → 完成
   异常 → 立即推送主管医生
```

## 四、模板实例化算法

这是规则引擎的核心。伪代码如下：

```java
/**
 * 由一次住院生成随访计划与任务
 * 幂等：重复执行不会产生重复数据
 */
public void instantiate(Encounter encounter) {

    // ---- 步骤 1：匹配模板 ----
    List<FollowupTemplate> matched = templateMatcher.match(
        encounter.getDiagnoses(),      // 出院诊断
        encounter.getProcedures(),     // 手术/操作
        encounter.getIcdCodes()
    );
    // matched 可能有多条 → 支持多路径并行
    // matched 为空 → 记入「待指定路径」，等护士长手工选

    for (FollowupTemplate tpl : matched) {

        // ---- 步骤 2：确定时间锚点 ----
        ZonedDateTime anchor = resolveAnchor(encounter, tpl);
        // 规则见第五节；锚点缺失时抛出可读异常，不静默失败

        // ---- 步骤 3：创建计划（数据库唯一索引保证不会重复）----
        FollowupPlan plan = planRepo.upsert(encounter, tpl, anchor);

        // ---- 步骤 4：遍历条目生成任务 ----
        for (TemplateItem item : tpl.getItems()) {

            // 4.1 求值分支条件；不满足则跳过
            if (!conditionEvaluator.eval(item.getConditionJson(), ctx(encounter, plan))) {
                continue;
            }

            // 4.2 计算应完成时间
            ZonedDateTime dueAt = calcDueAt(anchor, item);

            // 4.3 决定责任人
            Long assignee = resolveAssignee(item.getExecutorRole(), plan);

            // 4.4 幂等写入（唯一索引兜底）
            taskRepo.insertIfAbsent(plan, item, dueAt, assignee);
            // 等价 SQL: INSERT ... ON CONFLICT DO NOTHING

            // 4.5 留痕
            taskLogRepo.append(task, "CREATE", null, "由模板实例化生成");
        }
    }
}
```

## 五、时间锚点与日期推算

### 5.1 锚点优先级

```
1. anchor_event = SURGERY
   → 取本次住院的【主手术】procedure_date（精确到时分）

2. anchor_event = DISCHARGE
   → 取 discharge_date，时刻默认 09:00

3. anchor_event = ADMISSION
   → 取 admit_date，时刻默认 09:00

4. anchor_event = PATHOLOGY_REPORT
   → 事件型，不预先计算，等病理发布时触发（见第六节）

5. 锚点全部缺失
   → 计划标记为「待完善锚点」，列入护士待办，人工补齐后自动继续
      绝不静默跳过（静默跳过 = 患者被漏访）
```

### 5.2 为什么锚点要精确到时分

第 5 轮讲过 ERCP 的例子：手术 9-01、出院 9-05。
更极端的情况：

| 情形 | 处理 |
|---|---|
| 患者上午手术、下午出院（同日） | 用手术时刻 14:00 作为锚点，不是 00:00 |
| 患者跨零点手术（急诊 ERCP 凌晨 1:00 做） | 锚点仍是手术那一刻，术后 4 小时监测 = 当天 05:00 |

**对 ERCP 术后胰腺炎的 4 小时监测，差几个小时就是差一个级别。**

### 5.3 计算规则

```java
ZonedDateTime calcDueAt(ZonedDateTime anchor, TemplateItem item) {
    // 1. 按天偏移（业务口径：按自然日计算）
    LocalDate dueDate = anchor.toLocalDate().plusDays(item.getOffsetDays());

    // 2. 归一到提醒时刻（默认 09:00，可按条目覆盖）
    LocalTime dueTime = item.getDueTime() != null ? item.getDueTime() : LocalTime.of(9, 0);

    ZonedDateTime due = dueDate.atTime(dueTime).atZone(SHANGHAI);

    // 3. 节假日策略（默认不跳过 —— 医疗随访与工作日业务不同）
    if (item.isWorkdayOnly() && !holidayCalendar.isWorkday(dueDate)) {
        due = nextWorkday(due);
    }
    return due;
}
```

### 5.4 关于节假日的一个建议

**默认不跳过节假日。** 理由：

- 术后 3 天回访是**临床需要**，不是办公流程，周六周日同样要做；
- 如果自动顺延到周一，患者实际上被延迟了 2 天，可能错过并发症窗口；
- 但可以**配置**某些条目"仅工作日"（比如"门诊复诊预约提醒"这类行政性提醒）。

## 六、三类触发器的实现

### 6.1 时间型（占绝大多数）

由锚点 + 偏移天数算出，在实例化时一次性生成。

```
术后 3 天电话回访     → anchor=SURGERY,   offset=3
出院 1 个月门诊复查   → anchor=DISCHARGE, offset=30
```

### 6.2 事件型

**不能预先计算**，必须等事件发生。实现方式是在业务动作上挂钩子：

| 事件 | 钩子位置 | 生成什么 |
|---|---|---|
| 病理报告发布 | `pathology_report.status → PUBLISHED` 之后 | 「通知患者查看病理报告」任务 |
| 病理报告发布（高风险） | 同上 | 「3 个月后复查」任务（视风险等级） |
| HP 根除治疗结束 | 护士录入 HP 治疗方案与结束日期 | 「治疗结束 4–8 周复查呼气试验」 |
| 手术记录补录 | `medical_procedure` 新增 | 重新计算所有 SURGERY 锚点任务 |
| 计划人工调整 | 医生修改计划 | 撤销旧任务、生成新任务（保留流水） |

**实现要点**：钩子执行的是"**重新扫描该计划并补生成缺失的任务**"，
而不是"直接插入一条任务"。因为扫描本身是幂等的，即使钩子重复触发也不会出错。

### 6.3 条件型

由 `condition_json` 描述，支持嵌套组合：

```json
// 幽门螺杆菌阳性才生成复查任务
{ "all": [ { "field": "hp_status", "op": "eq", "value": "POSITIVE" } ] }

// 诊断含"胃溃疡"或"胃窦溃疡"
{ "any": [
    { "field": "diagnosis", "op": "contains", "value": "胃溃疡" },
    { "field": "diagnosis", "op": "contains", "value": "胃窦溃疡" }
] }

// 年龄 >= 70 且 不是单纯息肉
{ "all": [
    { "field": "age", "op": "gte", "value": 70 },
    { "not": { "field": "diagnosis", "op": "contains", "value": "息肉" } }
] }
```

**操作符**：`eq` `ne` `in` `contains` `gt` `gte` `lt` `lte` `exists` `isnull`

**可用字段**：`diagnosis` `icd_code` `procedure_name` `age` `gender`
`hp_status` `pathology_risk` `pathology_conclusion` `discharge_type` 等。

**关键设计**：条件在**两个时机**求值

| 时机 | 用途 |
|---|---|
| 实例化时 | 决定这个条目要不要生成 |
| 事件发生后 | 条件可能从"不满足"变为"满足"（如病理结果出来后 `pathology_risk` 变成 HIGH） |

所以事件钩子必须触发一次**全量重新求值**，这就是"病理为恶性自动转入肿瘤随访"的实现方式。

## 七、提醒调度器

### 7.1 调度频率

**每小时执行一次**（不是每分钟）。理由：

- 提醒粒度是"小时"，不是"秒"；
- 每小时一次对数据库压力可以忽略（几万条任务一次扫描 < 100ms）；
- 出错时最多延迟 1 小时，业务可接受。

### 7.2 一次调度的完整逻辑

```java
@Scheduled(cron = "0 5 * * * *")   // 每小时的第 5 分钟
public void dispatchReminders() {

    // 0. 全局开关与免打扰检查
    if (isQuietHour(now)) return;          // 22:00–07:00 直接跳过

    // 1. 取需要提醒的任务（走索引，不做全表扫描）
    List<Task> candidates = taskRepo.findNeedRemind(now);
    // SQL: WHERE status IN ('PENDING','DOING')
    //        AND due_date <= :today
    //        AND (last_remind_at IS NULL OR last_remind_at < :threshold)

    for (Task t : candidates) {

        // 2. 判断本次是否应该提醒（按策略计算）
        if (!reminderPolicy.shouldRemind(t, now)) continue;

        // 3. 组装脱敏消息
        Message msg = buildMaskedMessage(t);

        // 4. 按渠道矩阵依次投递（失败自动降级到下一层）
        for (Channel ch : channelChain.orderedFor(t)) {
            if (channelSender.send(ch, msg)) break;
        }

        // 5. 更新状态 + 留痕（这一步保证不会重复轰炸）
        t.setLastRemindAt(now);
        t.setRemindCount(t.getRemindCount() + 1);
        taskRepo.save(t);
        taskLogRepo.append(t, "REMIND", null, ch.getCode());
    }
}
```

### 7.3 提醒策略计算（T-1 / T 日 / 逾期）

| 阶段 | 判断条件 | 提醒时机 |
|---|---|---|
| **T-1 预告** | `due_date = 明天` 且 当前时间 ≥ 18:00 | 每天 1 次 |
| **T 日汇总** | `due_date = 今天` 且 当前时间 ≥ 08:00 | 每天 1 次（08:00） |
| **T 日催办** | `due_date = 今天` 且 未完成 | 距离上次提醒 ≥ 2 小时 |
| **逾期 1–3 天** | `due_date < 今天` 且 未完成 | 每天 3 次（08:00/12:00/17:00） |
| **逾期 4–14 天** | 同上 | 每天 1 次（08:00） |
| **逾期 > 14 天** | 同上 | 停止主动提醒，仅进逾期看板 |

### 7.4 免打扰与降频的边界情况

| 情况 | 处理 |
|---|---|
| 提醒时刻正好落在 22:00 之后 | 顺延到次日 07:00 后第一次调度 |
| 任务在免打扰时段被创建 | 不立即提醒，等次日 |
| 任务被标记为"紧急"（如术后 4 小时监测） | **允许穿透免打扰**（这是唯一例外） |

## 八、并发控制：两个护士同时点"开始回访"

这是必然会发生的情况（同组护士看到同一个待办）。如果不处理，
两个人会同时打电话给同一位患者，患者收到两通电话——**这是很糟糕的体验**。

### 8.1 抢占锁（乐观锁）

```sql
UPDATE followup_task
SET locked_by = :staffId,
    locked_at = now(),
    status    = 'DOING'
WHERE id = :taskId
  AND status = 'PENDING'
  AND (locked_by IS NULL OR locked_at < now() - interval '30 minutes');
  -- 30 分钟无操作自动释放，防止有人点了不干活把任务锁死
```

**返回 0 行 = 别人正在处理**，界面提示：

```
该任务正在由 王护士（N0455）处理中
[ 等待 ]  [ 强制接管 ]   ← 强制接管留审计日志
```

### 8.2 搭档协作的两种情况

| 情况 | 系统行为 |
|---|---|
| 医生在执行 | 护士看到"李医生处理中"，可等待 |
| 医生休假未执行，护士主动代做 | 护士可"强制接管"，完成后 `executor_staff_id = 护士`，责任人仍是医生 |

## 九、幂等性：三层防护

"重复执行不产生重复数据"在定时任务系统里是最容易出错的地方。我用三层防护：

| 层 | 手段 | 防什么 |
|---|---|---|
| 第 1 层 | 数据库唯一索引 `uk_task_plan_item(plan_id, template_item_id)` | 从根上杜绝重复任务 |
| 第 2 层 | `INSERT ... ON CONFLICT DO NOTHING` | 重复执行不报错、不产生垃圾 |
| 第 3 层 | 提醒前检查 `last_remind_at` | 同一小时内不重复发送 |

### 实测结果

```
第一次跑调度：tasks_after_first_run  = 1
第二次跑调度：tasks_after_second_run = 1     ← 没有增加

PASS 5.2 已拦截重复任务
        -> duplicate key value violates unique constraint "uk_task_plan_item"
```

## 十、任务状态机

```
                  ┌──────────┐
      生成 ───────►│ PENDING  │ 待处理
                  └────┬─────┘
       ┌───────────────┼──────────────┬────────────────┐
       ▼               ▼              ▼                ▼
  ┌────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
  │ DOING  │   │ SKIPPED  │   │CANCELLED │   │ EXPIRED  │
  │ 处理中 │   │  已跳过  │   │  已取消  │   │  已过期  │
  └───┬────┘   └──────────┘   └──────────┘   └──────────┘
      │           （护士标记）   （计划撤销）    （超14天）
      ▼
  ┌────────┐
  │  DONE  │ 已完成（已填回访记录）
  └───┬────┘
      │ 需重做
      ▼
  ┌─────────┐
  │ REOPEN  │ → 回到 PENDING（留流水）
  └─────────┘
```

**注意**：`SKIPPED` 和 `CANCELLED` 都**必须填写原因**，并进入审计。
因为"这条随访为什么没做"是质控和纠纷举证时的关键问题。

## 十一、异常处理：随访中发现异常怎么办

这是整个系统最有价值的功能之一。护士打电话时发现患者"再次呕血"，
系统必须**立即**把这件事推到主管医生面前，而不是等护士填完表单。

### 11.1 异常处理流程

```
护士勾选"明显异常"或勾选任一危险症状（呕血/黑便/便血/发热/黄疸）
   ▼
① 立即（不等提交）弹出确认框：
   「该患者存在异常症状，是否立即通知主管医生？」
   [ 立即通知 ]  [ 仅记录 ]
   ▼
② 选"立即通知" → 系统立刻推送主管医生（所有可用渠道）
   + 生成一条【紧急随访任务】，15 分钟内必须响应
   + 记录 followup_task_log(action='ESCALATE')
   ▼
③ 回访记录 is_abnormal = true
   ▼
④ 主管医生处理后，填写处理意见，任务关闭
```

### 11.2 为什么"不等提交"

因为护士在电话里听到"患者吐血了"，接下来还要聊 3 分钟、填 5 个字段、
可能被别的事打断——**这 10 分钟对消化道出血患者可能是致命的**。

**"立即通知"必须是一键完成的动作，不能有任何前置步骤。**

## 十二、边界情况清单（最容易出 BUG 的地方）

我把开发时必须逐个处理的情况列在这里，这条清单会直接变成测试用例：

| # | 情况 | 正确处理 |
|---|---|---|
| 1 | 出院当天又住院（同一次住院被录两次） | 住院号唯一索引拦截；提示"已存在" |
| 2 | 手术日期晚于出院日期（录错） | CHECK 约束 + 界面校验拦截 |
| 3 | 同一患者两条路径，任务时间点相同 | 允许，两条任务独立，界面合并显示为一条待办含两个路径 |
| 4 | 患者无手机，只有家属号码 | 使用 `patient_contact`，回访记录里记录"联系的是儿子" |
| 5 | 随访任务生成时医生已离职 | 任务指派失败 → 进入"待分配"列表，由护士长处理 |
| 6 | 任务到期前计划被修改 | 撤销未完成任务、生成新任务，旧任务保留 CANCELLED 流水 |
| 7 | 患者在随访期内死亡 | 计划关闭，剩余任务 CANCELLED（原因：患者已故），不再提醒 |
| 8 | 同一天生成几十条任务 | 汇总成一条"今日有 N 条待办"，不逐条轰炸 |
| 9 | 手机时间被手动改到未来 | 服务端时间为准，客户端时间仅用于显示 |
| 10 | 护士点了"开始"但没提交就关掉 App | 30 分钟锁自动释放，任务回到 PENDING |
| 11 | 导入 Excel 中途断电 | 事务保护，要么全成功要么全回滚 |
| 12 | 时区问题（服务器在 UTC） | 全程使用 `Asia/Shanghai`，锚点带时区 |
| 13 | 闰年 2 月 29 日 + 1 个月 | `LocalDate.plusMonths` 自动处理 |
| 14 | 病理报告发布后又撤回 | `RETRACTED` 状态，患者端同步隐藏，留审计 |
