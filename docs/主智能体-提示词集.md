## 二、为什么这么改（和用户原稿的差异清单）

| 原稿 | 问题 | 本版改成 |
|---|---|---|
| `begin -Stage fix` | 参数名不对，实际接口是 `-Action begin -Feature "<名>" -Stage fix` | 按 `tools\loop-guard.ps1` 的真实参数写 |
| 第 4 步"确认 .gitignore 里有 dist-deploy/ 和 output/" | 那两项**当时并不在** .gitignore 里 | 改成"先确认，缺了就补；但别忽略 tools\.pipeline\" |
| 第 2 步"用工具验证：后端构建 + 三套接口冒烟 + 三端浏览器走查" | 没说口令从哪来、没说 SKIP 怎么办、走查要先起 dev server | 补全：口令向用户要、SKIP≠通过且要单独说明、走查前起 5173–5175 |
| 未提及 `PortalAuthService.java` 被改的性质 | 会让新会话误判"代码被人偷偷改了" | 指明那是安全加固轮次的正当改动，并给出证据文档 |
| 第一批 B3/B4/B5 | **这三项已经做完并上线验证**，照做等于重复劳动 | 改为从 C8 开始，并说明 B3/B4/B5 的闭环证据在哪 |
| 未提台账收尾 | 只写了 begin，没写 end 与 `-Signature` | 明确 end 必填 `-Signature`（否则关掉一条熔断） |
| 未提演示数据会被测试消耗 | 跑几轮后面待办空了，会误判成"代码坏了" | 在检查清单与收尾里写明跑完 `demo-reset.ps1` |
| 未提"改了前端要三端都验" | 三份前端共用一套后端与样式约定，只验一端容易漏 | 写进第 4 步 |
| 报告要求偏笼统 | 容易收到"基本可用"这种无法验证的结论 | 给定固定格式：闸门/构建/冒烟/走查/版本控制/结论 |
