## 一、十几万条数据到底意味着什么（量化论证）

你的担心很自然，但结论是：**十几万条对一个现代关系型数据库来说，属于"几乎不存在"的量级。**

### 1.1 四年后的真实数据量测算

按一个临床科室、4 年、覆盖 10 万患者估算（这已经远超你说的"十几万条"）：

| 表 | 4 年预估行数 | 单行约 | 占用 |
|---|---|---|---|
| patient（患者） | 100,000 | 0.5 KB | 50 MB |
| encounter（就诊/住院） | 150,000 | 0.8 KB | 120 MB |
| diagnosis（诊断） | 200,000 | 0.3 KB | 60 MB |
| followup_plan（随访计划） | 750,000 | 0.4 KB | 300 MB |
| followup_task（随访任务） | 750,000 | 0.8 KB | 600 MB |
| followup_record（随访记录） | 750,000 | 2 KB | **1.5 GB** ← 最大头 |
| notification_log（消息日志） | 3,000,000 | 0.3 KB | 900 MB |
| audit_log（审计日志） | 5,000,000 | 0.3 KB | 1.5 GB |
| **数据小计** | | | **约 5 GB** |
| 索引开销（约 60%） | | | 约 3 GB |
| **合计** | | | **约 8 GB** |

### 1.2 参照系

- 一台 2 核 4G、60 GB 系统盘的云服务器，**磁盘占用不到 15%**；
- PostgreSQL 官网公开的基准测试中，**单表 1 亿行**在普通硬件上配合正确索引仍能保持毫秒级查询；
- 我们的 8 GB，是它承受能力的**千分之一**。

### 1.3 为什么"数据多了会内存溢出"是个误解

这是最关键的一点，请务必理解：

> **数据库的数据放在磁盘上，不在内存里。内存只是用来缓存"最近被访问过的那一小部分"。**

PostgreSQL 默认只申请 128 MB 的 `shared_buffers` 做缓存，其余靠操作系统的文件缓存自动管理，
缓存不够时会**自动淘汰旧数据**，而不是报错。所以数据从 1 万条涨到 100 万条，
**内存占用曲线是平的，不是斜的**。

真正会导致"内存溢出"的只有四种情况，全都可以在代码层面杜绝：

| 真实风险 | 后果 | 我们的对策 |
|---|---|---|
| 查询没走索引，全表扫描 | 查询变慢，CPU 飙高 | 所有查询字段建索引，上线前逐条 `EXPLAIN` 审查 |
| 一次性把几十万条加载到程序内存 | **这才是真正的内存溢出** | 强制分页，导出走流式处理，禁止无 `LIMIT` 的列表接口 |
| 日志表无限增长拖慢备份 | 备份时间越来越长 | 日志表按月分区 + 定期归档 |
| 备份文件越堆越多把磁盘占满 | 服务写入失败 | 备份保留策略 + 磁盘告警 |

**结论：不需要微服务，不需要 K8s，不需要分库分表。**
这三样东西对科室级系统只会增加故障点和运维成本。真正需要做的是
**索引设计、分页控制、分区归档、备份演练**——这四件事才是"能稳定跑好几年"的实质。

## 二、"一年清理一次数据"——这里有个法律红线

你的想法是"内容覆盖，防止内存溢出"。工程上可以理解，但**在医疗系统里不能这么做**。

### 2.1 法规依据

《医疗机构病历管理规定（2013 年版）》第二十九条：

> 门（急）诊病历档案的保存时间**自患者最后一次就诊之日起不少于 15 年**；
> 住院病历档案保存时间**自患者最后一次出院之日起不少于 30 年**。

随访记录（电话随访内容、随访问卷、复诊结果）属于病历资料的组成部分。
**如果系统擅自删除，医院在医疗纠纷中将失去举证能力，这是院方绝对不能接受的风险。**

### 2.2 正确的"分层留存"策略

不是不能清，而是**分清什么能清、什么不能清**：

| 数据类别 | 留存策略 | 理由 |
|---|---|---|
| 患者、就诊、诊断、随访计划、随访记录 | **永久保留**（软删除，不物理删除） | 法定义务 |
| 审计日志 | 保留 3 年，之后归档到冷存储 | 等保要求可追溯 |
| 消息发送日志 notification_log | 保留 12 个月后清理 | 仅用于排障与对账 |
| 短信记录 | 保留 24 个月 | 计费对账 |
| 设备推送 token、登录会话、验证码 | 过期即清（天级） | 无长期价值 |
| 临时文件、导出文件 | 保留 7 天 | 防止磁盘堆积 |

### 2.3 归档而非删除的技术实现

```sql
-- 日志类大表按月分区（PostgreSQL 原生分区表）
CREATE TABLE notification_log (
    ...
) PARTITION BY RANGE (created_at);

-- 每月自动建下个月的分区
-- 超过保留期的分区：先 DETACH（数据还在，只是不再查询），
-- 归档到对象存储/本地冷目录后再 DROP
```

**好处**：删除一整月的数据只需毫秒级（`DROP` 一个分区），
而 `DELETE 300 万行` 会锁表、产生大量 WAL、拖垮数据库。
这是"清理数据"唯一正确的做法。

另外，所有业务表的"删除"一律采用**软删除**（`deleted_at` 字段），
界面上看不到，数据库里还在，必要时可恢复，也满足审计要求。

## 三、"闹钟式弹屏"——这是本轮最重要的技术真相

你的需求描述是：三天后医生手机自动弹出提醒，像闹钟一样。
**这个需求在技术上有硬边界，必须现在说清楚，否则会做出一个"看起来有、实际收不到"的功能。**

### 3.1 各平台的真实能力

| 平台 | 能否后台定时弹窗 | 原因 |
|---|---|---|
| **微信小程序** | ❌ **完全不能** | 小程序关闭后代码不执行，微信不允许小程序后台常驻 |
| **安卓 App** | ✅ **可以，接近闹钟效果** | 系统级定时器 + 前台服务 + 高优先级通知 |
| **iOS App（不上架）** | ⚠️ 理论可以，但**没有分发渠道** | 本地通知可定时，但不走 App Store 就无法正规安装 |
| **iOS H5 / 微信内** | ❌ 不能 | 浏览器同样无后台执行 |

### 3.2 关于小程序，能做的其实只有两件事

1. **订阅消息**：用户点一次"允许"，你才能发**一条**通知（一次性订阅）。
   医疗类目可以申请**长期订阅**，但仍需用户主动授权，且审核严格；
2. **打开小程序时的红点/待办角标**：用户不打开就看不到。

所以，如果患者端和医护端都做成小程序，那么"三天后自动弹屏提醒医生回访"**这个功能根本不可能实现**。

### 3.3 我建议的三端分工（这是本轮的方案性结论）

| 端 | 形态 | 承担的任务 | 提醒能力 |
|---|---|---|---|
| **医护端（主力）** | **安卓 APK**，扫码安装 | 待办任务、电话回访登记、患者管理、计划制定 | **闹钟式弹窗 ✅**（定时器+前台服务+高优先级通知） |
| **医护端（补充）** | H5 网页（可加到手机桌面） | 备用查看、电脑端管理后台 | 打开时看待办 |
| **患者端** | 微信小程序 | 查复诊时间、看宣教、填问卷、看报告提醒 | 服务通知（需订阅授权）+ 打开看红点 |

**iOS 医护端怎么办？** 这是现实问题。因为不上架 App Store，iOS 没有正规分发渠道
（TestFlight 只有 90 天，企业签名证书极难获取且属灰色地带）。
**建议 iOS 医护用 H5**，并明确告知院方：iOS 上无法做到闹钟式自动弹窗，这是苹果系统的限制，不是我们的缺陷。
若院方坚持要 iOS 原生体验，唯一的正规路径是走 App Store 上架——那需要医院的开发者账号和资质，可列入第二期。

### 3.4 安卓端"闹钟式"的具体实现要点

要做到接近手机闹钟的效果，需要同时满足：

1. `AlarmManager.setExactAndAllowWhileIdle()` 精确闹钟；
2. 申请 `SCHEDULE_EXACT_ALARM` 权限（安卓 12+ 需用户手动授权）；
3. 前台服务 + 常驻通知，降低被杀概率；
4. 通知渠道设为"紧急"，才会横幅弹出并响铃；
5. 引导用户在系统设置中**关闭电池优化**、允许**自启动**（小米/华为/OPPO/vivo 各不同，需做引导页）；
6. **服务端定时任务兜底**：即使手机端定时器失效，服务端到点也会推送一次，
   用户下次打开 App 时待办列表一定存在（**这是最终的数据真相来源**）。

第 6 点特别重要：**待办列表永远是权威，弹窗只是提醒方式。**
这样即使所有推送都失效，任务也不会丢失。

## 四、隐私红线：通知栏里不能出现患者姓名和电话

你举的例子是：

> "您好主治医师，您 2026 年 10 月 3 日 14:00 手术的病人张大春，需要您及时回访。
> 病人信息：……电话……住址……"

**功能设计上完全合理，但直接推送这些内容到通知栏，会造成严重的隐私泄露。**

原因：

- 通知栏内容**在锁屏状态下任何人都能看到**（患者家属、同事、路人）；
- 安卓系统还会把通知同步到**智能手表、车机、蓝牙设备**；
- 三甲医院上线前要做**等级保护测评**，测评项里明确包含"敏感信息传输与展示保护"，
  这一条一定会被扣分并要求整改。

### 4.1 正确的两段式设计

**第一段（通知栏 / 锁屏）——脱敏**

```
🏥 随访待办提醒
您有 1 条术后随访任务待处理（今天 10:00）
点击查看详情
```

**第二段（打开 App 并验证身份后）——完整信息**

```
患者：张大春（男，58 岁）
住院号：2026****3721
手术：2026-10-03 14:00  内镜下结肠息肉切除术
主刀：李医生（工号 D0231）    主管护士：王护士（工号 N0455）
诊断：结肠息肉（待病理）

[📞 一键拨号 138****5678]   [ 👁 查看完整号码 ]  [ 📁 查看病历 ]
```

其中"查看完整号码"需要**再次确认身份**（指纹/面容/短密码），并在审计日志中记录：
`谁 / 何时 / 查看了哪个患者的哪个字段`。

### 4.2 可配置项

考虑到医院实际工作中的便利性，我会把它做成**可配置**：

| 配置项 | 默认值 | 可选 |
|---|---|---|
| 通知栏显示患者姓名 | 关闭（显示"有 N 条待办"） | 可开启 |
| 通知栏显示患者编号 | 开启（脱敏编号） | 可关闭 |
| 查看完整手机号是否需二次验证 | 开启 | 可关闭（不推荐） |
| 通知是否响铃/震动 | 开启 | 可关闭 |

**最终由医院信息科决定，我们不替医院做合规判断，但默认值取最保守的一档。**

## 五、预算现实：两三百元能做什么，不能做什么

我必须诚实地讲：**200–300 元可以做出一份能向院领导演示的成品，但无法支撑正式上线一年的运行。**
下面把账算清楚，并给出把成本压到最低的路径。

### 5.1 演示阶段（推荐先走这一步）

| 项目 | 费用 | 说明 |
|---|---|---|
| 云服务器（轻量应用服务器 2 核 4G） | **约 30–60 元/月**（按量或包月） | 演示 1 个月足够 |
| 域名（.cn 或 .top） | 约 29–40 元/首年 | 小程序要求 HTTPS 域名 |
| SSL 证书 | **0 元** | Let's Encrypt 免费自动续期 |
| 微信小程序账号 | **0 元** | ★见下方说明 |
| ICP 备案 | **0 元** | 但需 **2–3 周**，必须医院主体 |
| **合计** | **约 60–100 元** | 完全在你预算内 |

### 5.2 ★省钱关键：小程序可以复用医院公众号的主体资质

> 医院已经有一个**认证过的公众号**。微信官方允许**同一主体复用公众号资质注册小程序，免 300 元认证费**。

操作路径：小程序注册时选择"**复用公众号主体信息**"，用公众号管理员扫码确认即可。
这一步能直接省掉每年 300 元，是预算内最关键的一个操作。**请务必用这个方式，不要单独付费认证。**

### 5.3 正式上线阶段的真实成本（要提前知道）

| 项目 | 首年 | 第二年及以后 |
|---|---|---|
| 云服务器 2 核 4G | 99–299 元（新用户促销价） | **1,000–2,000 元** ⚠️ 续费涨价 |
| 域名 | 29–70 元 | 70–90 元 |
| 小程序 | 0 元（复用资质） | 0 元 |
| **合计** | **约 130–370 元** | **约 1,100–2,100 元** |

**⚠️ 这是最容易被忽略的陷阱：云厂商的首年促销价（99 元）和续费价（1,500 元）能差 15 倍。**
购买前一定要看"续费价格"，并优先选择 3 年期套餐（通常比年付再便宜 30–50%）。

### 5.4 把成本降到接近零的路径（我推荐）

> **上线时把系统部署到医院内网机房，由医院的服务器承载。**

理由：

- 三甲医院信息科**本来就有服务器和虚拟化平台**，分一台虚拟机给科室用是常见做法；
- 数据不出医院，**合规等级最高**，等保测评更容易通过；
- 医院**零额外采购成本**，你也不用承担续费；
- 患者小程序通过医院的**公网出口 / 反向代理**访问（需要信息科开端口并配置域名），
  这是三甲医院做自建小程序的**标准做法**。

**代价**：需要信息科配合，流程通常 1–3 个月。所以流程要**现在就开始走**，不要等系统做完。

### 5.5 预算外的必要支出（提前告知院方）

如果系统正式接入医院内网并与 HIS 对接，医院通常需要做**等级保护测评**，
费用约 **3–8 万元**（这是医院承担的合规成本，不是给你的）。
这件事你需要在适当的时候向科室主任或信息科提出，避免项目后期卡住。

## 六、HIS 实时接口对接的现实（第一版不要碰）

你说"每个工作人员可做 HIS 实时接口对接"。这个方向是对的，但我要提醒现实情况：

| 现实问题 | 说明 |
|---|---|
| HIS 由第三方厂商提供 | 三甲医院 HIS 多是东华、卫宁、创业慧康、东软等，接口不对外开放 |
| 需要多部门审批 | 信息科 + 医务处 + 厂商，流程通常 1–6 个月 |
| 通常要收费 | 单个接口开发费用从几千到几十万不等 |
| 安全限制严格 | HIS 在内网核心区，不允许外部系统直连，需通过前置机/数据交换平台 |

**第一版的正确做法**：

1. 数据靠**医护手工录入 + Excel 批量导入**（你已确认这条路可行）；
2. 数据表**预留 `his_patient_id`、`his_visit_id` 等字段**，
   以后接入 HIS 时只需回填，**不用改表结构、不用数据迁移**；
3. 把"Excel 导入"做得极其扎实：模板下载、字段校验、错误行回显、重复检测、
   导入预览、失败回滚。**这一块做好了，信息科才会认可你。**

## 七、技术栈定版建议

基于"国内、三甲医院、单人开发、预算敏感、要跑好几年"这四个约束：

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | **Spring Boot 3.5 + JDK 21 LTS** | 国内医疗行业主流（HIS 厂商同栈），LTS 支持到 2031 年，以后对接 HIS 无障碍 |
| 数据库 | **PostgreSQL 16** | 行级安全策略天然适配"护士只看自己主管患者"；JSONB 存随访模板；文档完善 |
| 缓存/队列 | **Redis 7** | 会话、验证码、延迟任务队列 |
| 定时调度 | **Spring Scheduling + 数据库任务表** | 不引入 Quartz 集群等重型组件，用数据库保证幂等 |
| 消息推送 | 安卓端本地通知 + 服务端推送（极光/个推免费额度，或自建） | 短信暂不用 |
| 医护端 | **uni-app（Vue 3 + TypeScript）** 打包安卓 APK + H5 | 一套代码出两端，节省单人开发的工作量 |
| 患者端 | **微信小程序（uni-app 同代码库编译）** | 复用同一套业务代码，避免写两遍 |

## 八、真实随访路径建模（基于你提供的张大春案例）

你的案例信息量很大，我把它拆解成系统需要的**六个要素**：

```
触发事件（手术/出院）+ 相对时间（术后 3 天）+ 责任人（主刀医生）
  + 执行方式（电话回访）+ 随访内容（术后恢复情况）+ 协助人（护士可代录）
```

这六个要素就是**随访路径模板（Follow-up Pathway Template）**的结构。
下面是我根据临床常规做的三条真实路径，**请你让科室医生核对修正**（这一步非常重要，
我不能替医生做临床判断）：

### 路径 1：内镜下结肠息肉切除术后（对应张大春的案例）

| 时间点 | 执行人 | 方式 | 内容 |
|---|---|---|---|
| 术后 1 天 | 主管护士 | 电话/小程序 | 有无腹痛、便血、发热（**并发症预警，异常立即上报医生**） |
| 术后 3 天 | **主刀医生** | **电话回访** | 术后恢复、腹痛、排便、饮食、用药依从性 ← 你举的例子 |
| 病理报告出具后 | 系统通知 | 小程序 | 通知患者领取病理报告（可由护士上传报告结论） |
| 术后 1 个月 | 主管护士 | 电话回访 | 恢复情况、复诊提醒 |
| 术后 6–12 个月 | 系统通知 | 小程序 | 复查肠镜提醒 |
| **若病理为高级别上皮内瘤变/癌** | 自动转入肿瘤随访路径 | — | 术后 3/6/12 个月复查，优先级提升 |

> 最后一条是**规则化的分支**：同一个手术，病理结果不同，随访路径不同。
> 这正是"根据病情推送不同内容"的真实含义，也是规则引擎必须存在的原因。

### 路径 2：腹腔镜胆囊切除术后

| 时间点 | 执行人 | 方式 | 内容 |
|---|---|---|---|
| 术后 2 天 | 主管护士 | 电话 | 切口疼痛、体温、饮食 |
| 术后 7 天 | 主刀医生 | 电话/门诊 | 切口愈合、复查换药 |
| 术后 1 个月 | 主管护士 | 电话 | 消化功能、饮食耐受 |
| 术后 3 个月 | 主管护士 | 电话 | 远期恢复情况 |

### 路径 3：2 型糖尿病出院随访

| 时间点 | 执行人 | 方式 | 内容 |
|---|---|---|---|
| 出院 3 天 | 主管护士 | 电话 | 血糖监测频率、用药依从性、低血糖症状 |
| 出院 1 周 | 患者自行 | 小程序问卷 | 上传 7 天空腹/餐后血糖记录 |
| 出院 1 个月 | 主管医生 | 门诊 | 复查血糖、调整方案 |
| 出院 3 个月 | 主管医生 | 门诊 | 复查糖化血红蛋白 |

### 关于"护士协助上传记录"

你提到"护士能帮着上传这些记录"，这一点非常重要，且需要**明确的业务规则**：

1. 系统为每个随访任务标注**责任人（医生）**和**可协助人（护士）**；
2. 护士可以**代录随访结果**，但记录中必须同时保存
   `任务责任人` 和 `实际执行人` 两个字段；
3. 若护士实际执行，医生端会收到"该任务已由 XX 护士完成"的提示，避免重复拨打；
4. 医生端可查看由护士代录的完整记录（只读），并可补充意见。

**这就是"护士能帮着上传"在数据层面的正确实现方式**——
既方便协作，又不会造成"谁做的说不清"，这在医疗场景里是要命的细节。
