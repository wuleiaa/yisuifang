## 三、三个关键设计决策（这是本轮的技术核心）

### 3.1 主键策略：内部 BIGINT + 对外 UUID

**每张业务表都有两个 ID：**

```sql
id         BIGSERIAL PRIMARY KEY,                        -- 内部主键，性能好
public_id  UUID NOT NULL DEFAULT gen_random_uuid(),      -- 对外暴露，不可枚举
```

**为什么要这样？**

如果接口直接暴露自增 ID（`/api/patient/1001`），任何人把 1001 改成 1002
就能遍历全科室的患者数据。**这是最常见的越权漏洞之一。**

用 UUID 对外，即使链接被转发、被截图，也无法推算出其他患者的地址。
内部仍用 BIGINT 做主键和外键，**性能不受影响**（UUID 索引会大得多）。

### 3.2 手机号加密：三重字段设计

手机号是敏感个人信息，既要**安全**又要**能查**。这是医疗系统的经典难题
（加密后就没法用 `WHERE phone = ?` 查询了）。解决方案是**一个手机号存三个字段**：

```sql
phone_cipher  BYTEA        -- 密文：AES-256-GCM(明文, 数据密钥)
phone_hash    VARCHAR(64)  -- HMAC-SHA256(明文, pepper)，用于等值查询
phone_mask    VARCHAR(20)  -- "138****5678"，列表页直接展示
```

**三个字段各司其职：**

| 场景 | 用哪个字段 |
|---|---|
| 列表页显示 | `phone_mask`（不解密，性能好，也不会泄露） |
| 按手机号查患者 | `phone_hash`（等值查询，走索引，不可逆） |
| 打电话/导出/发给患者 | 解密 `phone_cipher`，**同时写审计日志** |

**密钥管理（这是最容易被做错的地方）：**

| 密钥 | 存放位置 | 绝不能放在哪 |
|---|---|---|
| 数据密钥（AES） | 服务器环境变量 / 密钥文件（权限 600） | ❌ 数据库里、❌ 代码里、❌ Git 里 |
| pepper（HMAC 盐） | 同上，与数据密钥**分开存放** | 同上 |

**部署时我会提供一个 `generate-keys` 脚本**，随机生成两把密钥并写入配置文件，
同时输出"密钥备份提示"——**密钥丢了，所有手机号就再也解不开了**，
所以必须单独备份。

**为什么不用 MD5/SHA256 裸哈希手机号？**
因为手机号只有 11 位、号段有限，攻击者用一张彩虹表几秒钟就能反查出来。
必须加 pepper（密钥盐）才有意义。

### 3.3 行级权限：数据库层的第二道防线

第 1 轮定的铁律是"护士只能看自己主管的患者"。这件事**必须在数据库层也强制一遍**，
因为只要有一处代码忘了加权限过滤，数据就漏了。

PostgreSQL 原生支持行级安全策略（RLS），用法：

```sql
ALTER TABLE followup_task FORCE ROW LEVEL SECURITY;

CREATE POLICY p_task_access ON followup_task
    USING (
        current_setting('app.is_system', true)  = 'true'    -- 后台任务
        OR current_setting('app.is_manager', true) = 'true'  -- 护士长/主任
        OR assignee_staff_id = <当前登录人>                    -- 责任人
        OR care_team_id IN (<当前登录人所在的搭档组>)            -- 同组护士
    );
```

**应用在每次请求开始时执行：**
```sql
SET LOCAL app.current_staff_id = '231';
SET LOCAL app.is_manager      = 'false';
```

**效果**：一个护士执行 `SELECT * FROM followup_task`，
数据库**只会返回她有权看到的行**——即使程序写错了也漏不出去。

> ⚠️ 一个必须注意的前提：**应用必须用独立账号 `app_rw` 连接数据库，
> 不能用表属主账号**。因为表属主默认绕过 RLS。
> 这一点我在 SQL 脚本里已经处理好了（自动创建 `app_rw` 角色）。

> ⚠️ 部署时请务必修改脚本里 `CHANGE_ME_ON_DEPLOY` 的默认密码。

## 四、病理发布闸门：在数据库层强制

第 3 轮定的规则是"高风险病理必须已告知患者才能发布"。
我把它做成了**数据库触发器**，而不是只写在 Java 代码里：

```sql
CREATE TRIGGER tg_pathology_publish_gate
    BEFORE INSERT OR UPDATE ON pathology_report
    FOR EACH ROW EXECUTE FUNCTION trg_pathology_publish_gate();
```

触发器会检查三件事，任何一条不满足就直接报错、拒绝写入：

| 检查 | 报错信息 |
|---|---|
| 是否经医生审核 | 病理报告必须经主管医生审核后才能发布 |
| 是否填写医生解读 | 病理报告必须填写医生解读后才能发布 |
| 高风险是否已告知 | 高风险病理报告必须先完成患者告知才能发布 |

**为什么放在数据库层？**

因为这是**医疗安全红线**。放在 Java 层，将来某次重构、某个新接口、
某次批量脚本都可能绕过它；放在数据库层，**没有任何办法绕过**。

## 五、随访时间的锚点规则（实现细节）

第 5 轮定的规则"有手术日期按手术日期算"，落到数据模型上是这样：

```sql
followup_plan.anchor_procedure_at    -- 锚点 1：手术/操作时间
followup_plan.anchor_discharge_date  -- 锚点 2：出院日期
```

**生成任务时的计算优先级：**

```
1. 若存在 medical_procedure 记录 → 用 procedure_date 作为锚点
2. 否则若 encounter.discharge_date 存在 → 用出院日期作为锚点
3. 否则 → 报错，提示"缺少随访时间锚点，无法生成计划"
```

举例说明为什么这条规则重要：

| 患者 | ERCP 手术 | 出院 | 「术后 3 天」应为 | 若按出院算（错误） |
|---|---|---|---|---|
| 甲 | 9-01 | 9-05 | **9-04** | 9-08（晚 4 天） |
| 乙 | 9-01 | 9-01（当天出院） | 9-04 | 9-04（一致） |

**对 ERCP 术后胰腺炎的监测，这 4 天差不起。**

### 7.2 ★ 测试中发现的一个重要陷阱（已记录进设计）

第一次跑 RLS 测试时，"无关护士"竟然看到了全部数据。

**原因**：测试连接用的是 `postgres` 超级用户，而**超级用户会绕过行级安全策略**，
即使表上加了 `FORCE ROW LEVEL SECURITY` 也一样。

**这意味着**：如果应用图省事直接用数据库属主账号连接，
那么辛苦设计的行级权限**一点作用都不会有**，而且不会有任何报错提示，
你会以为它是生效的。

**结论（已写入铁律）**：

> 应用连接**必须**使用 `app_rw` 这个非超级用户账号，
> 部署后**必须**跑一遍冒烟测试确认 `is_super = f`。
> 我会把这一步写进第 9 轮的部署检查清单。

## 十、本轮需要你回答的问题（3 个）

1. **服务号的订阅通知模板**，能否请宣传科/信息科帮忙申请？
   需要的信息是**模板 ID**。如果暂时申请不下来也没关系，
   小程序订阅消息那条路照样能保证 iOS 收到提醒，不影响开发进度。

2. **一个患者出院后，需不需要能"同时走两条路径"？**
   举例：患者既有"胆总管结石（ERCP 术后）"又有"胆囊结石（胆囊切除术后）"，
   两条路径需要并行随访吗？还是合并成一条？
   （技术上都支持，我倾向于**允许多条路径并行**，任务各自独立。）

3. **回访记录的字段**，我先按这个设计，你看有没有要加的：
   是否接通 / 联系的是本人还是家属 / 通话时长 / 症状勾选（腹痛、便血、呕血、
   黑便、发热、黄疸、恶心呕吐、无明显症状）/ 恢复情况 / 用药依从性 /
   回访结论 / 指导建议 / 下一步（继续计划、提前复诊、上报医生、结束）。
   **有想加的直接说，改字段很容易；开发完再改就要动数据了。**
